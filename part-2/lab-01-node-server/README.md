## 1 Что сделано

REST API ресурса `diagrams` на Express 5 с данными в массиве в памяти. Диаграмма хранит `title`, `notation`, `sourceCode`, `priority`, `owner` и время создания `createdAt`.

| Метод    | Путь                         | Успех            | Ошибки                                    |
| -------- | ---------------------------- | ---------------- | ----------------------------------------- |
| `GET`    | `/diagrams`                  | 200, массив      |                                           |
| `GET`    | `/diagrams/:id`              | 200, объект      | 400 неверный id, 404 нет диаграммы        |
| `POST`   | `/diagrams`                  | 201 и `Location` | 400 неверные данные или JSON              |
| `PUT`    | `/diagrams/:id`              | 200, объект      | 400 неверный id или данные, 404           |
| `PATCH`  | `/diagrams/:id`              | 200, объект      | 400 неверный id, данные или пустое тело, 404 |
| `DELETE` | `/diagrams/:id`              | 204 без тела     | 400 неверный id, 404 (в том числе повтор) |
| любой    | неизвестный путь             |                  | 404 в формате JSON                        |
| другой   | `/diagrams`, `/diagrams/:id` |                  | 405 и заголовок `Allow`                   |

Ошибки всегда имеют вид `{ "error": "сообщение" }`, а для неверных данных добавляется `details` со списком полей. Непредвиденные сбои дают 500 без внутренних подробностей.

Поля: `title`, `sourceCode`, `owner` это непустые строки; `notation` одно из `UML`, `BPMN`, `ERD`, `DFD`, `IDEF0`, `Petri`; `priority` одно из `low`, `normal`, `high` (необязательно, по умолчанию `normal`). Лишние поля отбрасываются, `id` и `createdAt` назначает сервер, клиент их не задаёт.

`createdAt` это время создания в формате ISO 8601 (`2026-10-17T09:30:00.123Z`). У каждой записи оно уникально: если две записи созданы в одну миллисекунду, вторая получает значение на миллисекунду позже. Замена через `PUT` и правка через `PATCH` время создания не меняют, по нему можно сортировать: `GET /diagrams?sort=createdAt&order=desc`.

### PUT и PATCH: в чём разница

`PUT` заменяет запись целиком: нужно прислать все обязательные поля, а то, что не прислано, получит значение по умолчанию. `PATCH` меняет только присланные поля, остальные остаются как были. Например, `PATCH /diagrams/1` с телом `{"priority":"high"}` меняет один приоритет. Каждое присланное поле проверяется так же строго, как в `POST` и `PUT`, пустое тело или тело без известных полей даёт 400. Повторный `PUT` с тем же телом всегда даёт одно и то же состояние (идемпотентность), `PATCH` по определению идемпотентным не гарантируется, например при относительных изменениях вроде «увеличить на 1». В этой работе реализованы оба метода.

## 2 Запуск

Нужен Node.js 22 или новее.

```bash
cd part-2/lab-01-node-server
npm install
npm run dev     # nodemon, перезапуск при правках
npm start       # обычный запуск
npm test        # тесты и покрытие
```

Порт по умолчанию 3000. Чтобы сменить, скопируйте `.env.example` в `.env` и поправьте `PORT`; файл `.env` в репозиторий не попадает.

Примеры запросов для расширения REST Client в VS Code лежат в [`requests.http`](requests.http). Пример для curl:

```bash
curl -i -X POST http://localhost:3000/diagrams \
  -H "Content-Type: application/json" \
  -d '{"title":"Login flow","notation":"UML","sourceCode":"user -> server","owner":"carol"}'
```

## 3 Структура

| Путь                                     | Назначение                                                       |
| ---------------------------------------- | ---------------------------------------------------------------- |
| `server.js`                              | Точка входа: читает `.env`, запускает сервер                     |
| `src/app.js`                             | Сборка приложения `createApp(store)`: JSON, маршруты, ошибки     |
| `src/routes/diagrams.routes.js`          | Таблица маршрутов                                                |
| `src/controllers/diagrams.controller.js` | Обработчики запросов                                             |
| `src/models/diagram.model.js`            | Хранилище в массиве, допустимые значения полей, начальные данные |
| `src/middleware/validate.js`             | Проверка id и тела запроса                                       |
| `src/middleware/error-handler.js`        | Ответ 404 для неизвестных путей и глобальный обработчик ошибок   |
| `src/errors.js`                          | Класс `HttpError` и помощники                                    |
| `tests/diagrams.test.js`                 | тесты всех маршрутов, ошибок, `createdAt` и `PATCH`              |

Хранилище передаётся в `createApp` как параметр, поэтому тесты работают с чистыми данными, а в следующей работе массив заменяется базой данных без правки маршрутов.

## 4 Проверка

`npm test` запускает тесты на встроенном `node:test` с настоящими HTTP-запросами к серверу на свободном порту. В тот же запуск входит проверка сборки и оформления отчётов (`report.test.mjs`).

Известное замечание: `npm audit` показывает уязвимость зависимости `braces` в цепочке `nodemon`. Это инструмент разработки, он не попадает в рабочий запуск.

## 5 Ограничения и протокол

Пределы длины (`title` 80, `owner` 60, `sourceCode` 10000) и размер тела (`100kb`) лежат в [`limits.json`](limits.json). Пробельные значения считаются пустыми, `title` и `owner` обрезаются. Тело не в JSON даёт 415, слишком большое 413, `OPTIONS` отвечает 204 с `Allow`, `HEAD` работает как `GET`, на всех ответах стоят заголовки безопасности. Подробности в [`AUDIT.md`](AUDIT.md).
