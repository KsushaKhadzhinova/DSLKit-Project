# Практическое занятие 2. Проектирование и реализация REST API

Ветка репозитория: `pz22`.

Проект DSLKit (направление SaaS, вариант 26). REST API на Express 5 с тремя ресурсами: пользователи (`users`), проекты (`projects`), диаграммы (`diagrams`). Данные хранятся в массивах в памяти. Полное описание эндпоинтов, ошибок и примеры curl: [`API.md`](API.md). Отчёты: [`report.tpl.md`](report.tpl.md) на русском, [`report.en.tpl.md`](report.en.tpl.md) на английском.

## Запуск

Нужен Node.js 20 или новее.

```bash
cd part-2/pz-02-rest-api
npm install
npm start
```

Адрес API: `http://localhost:3000/api` (порт задаёт переменная `PORT`). Режим разработки с перезапуском: `npm run dev`. Тесты: `npm test`. Настройки окружения: образец [`.env.example`](.env.example) (`PORT`, `RATE_LIMIT_MAX`), загрузка командой `node --env-file=.env src/server.js`, файл `.env` в репозиторий не входит. Замечания аудита: [`AUDIT.md`](AUDIT.md).

## Что реализовано

- CRUD для каждого ресурса: список, одна запись, создание, полная замена (`PUT`), частичное изменение (`PATCH`), удаление.
- Дополнительные операции: диаграммы проекта `GET /api/projects/:id/diagrams`, публикация `POST /api/diagrams/:id/publish`, копирование `POST /api/diagrams/:id/duplicate`.
- Списки: фильтр по полю, поиск `q`, сортировка `sort`, страницы `page` и `limit`.
- Проверка входных данных: обязательные поля, типы, длина, перечисления, формат почты, неизвестные поля, существование связанных записей.
- Целостность: нельзя удалить пользователя с проектами и проект с диаграммами (409).
- Единый формат ошибок JSON и коды 200, 201, 204, 400, 403, 404, 405, 406, 409, 412, 413, 415, 429, 500.
- Заголовки безопасности (`Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`), ограничение частоты запросов (429), запись ошибок в журнал без переводов строк.

## Журнал запросов: как он работает

Журнал лежит в таблице БД `request_log` (SQLite, файл из `JOURNAL_FILE`, по умолчанию `journal.sqlite`). Порядок для каждого запроса простыми словами:

1. Сервер присваивает запросу Request ID (заголовок `X-Request-Id`).
2. До выполнения действия в таблицу пишется строка: время, метод, путь, адрес клиента, Request ID.
3. Если запись строки не удалась (таблица удалена, файл заблокирован, диск полон), действие **не выполняется**, клиент получает 5xx: JSON `journal_unavailable` или страницу 500 с Request ID. Работать без журнала запрещено. Причина пишется в консоль сервера.
4. Если запись удалась, действие выполняется, а в строку добавляется итоговый статус. Если действие закончилось ошибкой (400, 404, 409, 412), строка остаётся с этим статусом: журнал запросов хранит и неудачные попытки.
5. Не пишутся в журнал: `GET /health` (проверка работоспособности) и запросы, отклонённые ограничением частоты (429), их видно только по заголовку `X-Request-Id` и в ответе.

Запись журнала и действие над данными не лежат в одной транзакции СУБД, потому что данные ПЗ2 живут в массиве в памяти; правило «нет записи журнала, нет действия» выполнено порядком шагов. Если сбой случится уже после действия, при записи итогового статуса, ответ не меняется, строка остаётся без статуса, а ошибка пишется в консоль. Воспроизвести сбой: `node tools/break-journal.mjs <файл>` (подробности в `docs/HANDOVER-PZ2-CODE.md`).

## Роли и ответ 403

Входа в систему нет, личность задаётся заголовками: `X-User-Id` (номер пользователя) и `X-Role` (`user` по умолчанию или `admin`). Без `X-User-Id` запрос анонимный и не ограничен (так работали все запросы до ролей). С `X-User-Id` действуют правила:

| Действие | Обычный пользователь | Администратор (`X-Role: admin`) |
| --- | --- | --- |
| Менять или удалять свою запись пользователя | да | да |
| Менять или удалять запись другого пользователя | 403 | да |
| Менять свой проект, создавать проект на себя | да | да |
| Менять чужой проект, отдавать проект другому | 403 | да |
| Удалять проект (любой) | 403 | да |
| Диаграммы (изменить, удалить, publish, duplicate, создать) | только в своём проекте, иначе 403 | да |

Неверное значение заголовка даёт 400 `invalid_identity`, несуществующий пользователь в `X-User-Id` даёт 403. Сначала проверяется, что запись есть (404), потом права (403), потом тело запроса. Заголовки принимаются на веру: это учебное упрощение, настоящая система берёт личность из проверенной сессии. Сценарий гонки: пользователь добавляет диаграмму, пока администратор удаляет проект; результат всегда 201, 404 или 409, без 5xx и без «висячих» диаграмм.

Ошибки приходят в JSON (поля `code`, `message`, `title`, `description`, `requestId`) или, если браузер просит HTML, оформленной страницей с описанием и Request ID.
