Работа продолжает [лабораторную работу 2](../lab-02-sequelize): добавлены пользователи, регистрация, вход с JWT, защита маршрутов и ролевая модель. ## 1 Что сделано

| Метод           | Путь                         | Доступ             | Ответы                                                          |
| --------------- | ---------------------------- | ------------------ | --------------------------------------------------------------- |
| `POST`          | `/auth/register`             | все                | 201 пользователь без хеша, 400 неверные данные, 409 email занят |
| `POST`          | `/auth/login`                | все                | 200 `{ token, tokenType, expiresIn }`, 400, 401 неверная пара   |
| `GET`           | `/profile`                   | токен              | 200 текущий пользователь, 401                                   |
| `GET`           | `/diagrams`, `/diagrams/:id` | токен              | 200, 404                                                        |
| `POST`          | `/diagrams`                  | токен              | 201, владелец это вызывающий пользователь                       |
| `PUT`, `PATCH`, `DELETE` | `/diagrams/:id`     | владелец или admin | 200 или 204, 400, 403 чужая диаграмма, 404                      |
| `GET`           | `/users`                     | admin              | 200 список без хешей, 403                                       |
| `PATCH`         | `/users/:id/role`            | admin              | 200, 400 неверная роль или своя роль, 404                       |
| `DELETE`        | `/users/:id`                 | admin              | 204, 400 удаление себя, 404                                     |

**Дополнительный механизм: ролевая модель (RBAC).** Поле `role` (`user` или `admin`), middleware `requireRole('admin')`, маршруты управления пользователями и правило «менять и удалять диаграмму может владелец или admin». Роль при регистрации всегда `user`; первого администратора создаёт сид из переменных окружения.

## 2 Безопасность: решения

- Пароль хранится только как хеш bcrypt (10 раундов), длина пароля от 8 символов и не больше 72 байт (дальше bcrypt обрезает).
- Токен подписан HS256, срок жизни из `JWT_EXPIRES_IN` (по умолчанию 1 час). Проверка принимает только HS256, поэтому токены `alg: none` и HS512 отклоняются.
- После проверки подписи middleware читает пользователя из базы: удалённая учётная запись и смена роли действуют сразу, а `req.user` содержит `{ id, email, role }` из базы.
- Вход отвечает одинаково на неверный пароль и неизвестный email и тратит одинаковое время (сравнение с запасным хешем).
- Email приводится к нижнему регистру, дубликаты ловит уникальный индекс (ответ 409 и при гонке запросов).
- Секрет `JWT_SECRET` обязателен (от 32 символов), без него сервер не запускается. В репозитории только `.env.example`.
- Защита от перебора: 20 входов с адреса за 15 минут (ответ 429 и `Retry-After`), после 5 неудачных попыток почта блокируется на 15 минут, в том числе для неизвестных почт. Счётчики в памяти процесса. Срок токена не больше 24 часов, секрет от 32 символов, издатель `dslkit`, заголовки безопасности и журнал запросов в таблице `RequestLogs`. Общий предел: 300 запросов с адреса в минуту на все маршруты, кроме `/health` (ответ 429 и `Retry-After`, значения в `limits.json`, переопределение `GENERAL_RATE_MAX` и `GENERAL_RATE_WINDOW_MINUTES`). Он стоит перед журналом, поэтому отклонённые запросы не записываются в `RequestLogs` по одному: в консоль выводится одна строка на адрес и окно, а в таблицу попадают только принятые запросы. Пределы длины лежат в `limits.json`.
- Выход с отзывом токена и refresh-токены сделаны, см. раздел 8.

## 3 Запуск

Нужен Node.js 22 или новее. База данных PostgreSQL: локальный контейнер поднимается командой `docker compose up -d db` (пароль и `DATABASE_URL` в `.env`, образец в `.env.example`), Neon и Supabase подключаются через `DATABASE_URL` с `DATABASE_SSL=true`. SQLite остаётся только для тестов (`SQLITE_STORAGE`).

```bash
cd part-2/lab-03-auth
npm install
cp .env.example .env     # затем задайте JWT_SECRET, при желании ADMIN_EMAIL и ADMIN_PASSWORD
npm run db:migrate
npm run db:seed          # администратор (ADMIN_*), четыре демо-пользователя (DEMO_USER_PASSWORD), 32 демо-диаграммы
npm run dev
npm test
```

**Демонстрационные данные.** Сид состоит из трёх файлов. `…-admin-user.js` создаёт администратора из `ADMIN_EMAIL` и `ADMIN_PASSWORD` (минимум 10 символов). `…-demo-users.js` создаёт четырёх обычных пользователей alice, bob, carol и dave (`@example.test`, роль `user`) с общим паролем из `DEMO_USER_PASSWORD`. `…-demo-diagrams.js` добавляет 32 диаграммы по шести нотациям и пять «неудобных» строк (юникод, разметка, SQL-подобный текст, предельная длина); владельцы по очереди администратор и четыре пользователя, поэтому проверки роли и владельца есть на чём пробовать. Пароли берутся только из переменных окружения (имена в `.env.example`), в репозитории их нет, в базу попадает хеш bcrypt. Без переменной соответствующий шаг пропускается. Повторный запуск ничего не дублирует: существующий аккаунт не меняется, удалённая диаграмма возвращается. `db:seed:undo` удаляет только демонстрационные строки.

Секрет можно сгенерировать командой `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`. Примеры запросов для расширения REST Client лежат в [`requests.http`](requests.http). Пример для curl:

```bash
curl -s -X POST http://localhost:3000/auth/login -H "Content-Type: application/json" \
  -d '{"email":"alice@example.com","password":"correct horse 42"}'
curl -s http://localhost:3000/profile -H "Authorization: Bearer <token>"
```

## 6 PUT и PATCH

`PUT /diagrams/:id` заменяет диаграмму целиком: нужны все обязательные поля, пропущенный `priority` получает значение по умолчанию. `PATCH /diagrams/:id` меняет только присланные поля (например `{"priority":"high"}`), остальные остаются прежними. Каждое присланное поле проверяется как в `POST`, пустое тело или тело без известных полей даёт 400, поле владельца прислать нельзя. Права те же, что у `PUT`: менять может владелец или admin, остальные получают 403. `PUT` идемпотентен, `PATCH` по определению не обязан быть таким.

## 7 Как вызвать ответ 500 настоящим сбоем

Ответ 500 вызывается сбоем базы, а не кнопкой.

- SQLite: запустите `npm start`, во втором окне выполните `npx sequelize-cli db:migrate:undo:all`. Таблицы исчезают под работающим сервером, первый же запрос не может записать строку в журнал `RequestLogs` и получает 500 с телом `{ "error": "Internal server error" }`, подробности остаются только в консоли сервера. Вернуть работу: `npm run db:migrate` и `npm run db:seed`.
- PostgreSQL (Neon, Supabase или локальный): остановите службу или контейнер базы, запросы дают 500, а `GET /health` отвечает 503.
- Запуск при недоступной базе не завершается: сервер остаётся запущенным, в консоль пишется сообщение, `GET /health` и маршруты, которым нужна база, отвечают 503, пока база не станет доступной.

## 8 Расширенная аутентификация и авторизация

Добавлено сверх условия (запрос владельца). Все маршруты ниже; подробности по безопасности в списке под таблицей.

| Метод | Путь | Доступ | Назначение |
| ----- | ---- | ------ | ---------- |
| `POST` | `/auth/refresh` | refresh-токен в теле | Новая пара токенов, старый refresh-токен гасится |
| `POST` | `/auth/logout` | refresh-токен в теле | Закрывает сессию, ответ всегда 204 |
| `POST` | `/auth/logout-all` | токен | Закрывает все сессии |
| `GET` | `/auth/sessions` | токен | Список своих сессий (устройство, адрес, даты) |
| `DELETE` | `/auth/sessions/:id` | токен | Закрывает свою сессию, чужая даёт 404 |
| `POST` | `/auth/change-password` | токен | Смена пароля, остальные сессии закрываются |
| `POST` | `/auth/password-reset/request` | все | Одноразовый токен «письмом» (консоль или `MAIL_OUTBOX_FILE`), ответ всегда 202 |
| `POST` | `/auth/password-reset/confirm` | все | Новый пароль по токену, токен действует один раз и 30 минут |
| `GET` | `/auth/2fa` | токен | Состояние двухфакторной защиты |
| `POST` | `/auth/2fa/setup`, `/enable`, `/disable` | токен | TOTP (RFC 6238, `node:crypto`), 8 кодов восстановления |
| `POST` | `/auth/2fa/verify` | токен-вызов | Второй шаг входа: код или код восстановления |
| `GET` | `/admin/audit` | `audit:read` | Журнал событий безопасности (таблица `AuditEvents`) |
| `GET`, `POST` | `/admin/roles` | `role:read`, `role:manage` | Список ролей и создание своей роли из прав, которые есть у вызывающего |
| `DELETE` | `/admin/roles/:id` | `role:manage` | Удаление своей роли, если ею никто не пользуется |
| `GET` | `/admin/permissions` | `role:read` | Список прав |
| `POST` | `/users/:id/unlock` | `user:unlock` | Снять блокировку входа |

- Access-токен живёт 15 минут (HS256, `iss` и `aud` проверяются, допуск часов 5 секунд). Refresh-токен непрозрачный, в базе только его SHA-256, при каждом обмене заменяется. Повторное предъявление уже использованного токена закрывает всё семейство (сессию) и пишется в журнал.
- Секреты TOTP шифруются AES-256-GCM, ключ из `TWO_FACTOR_KEY` (или из `JWT_SECRET` с другой меткой), коды восстановления хранятся хешами, код того же шага времени второй раз не принимается.
- Пароль: от 8 символов, до 72 байт, не из списка частых, не равен email. Сброс пароля и вход отвечают одинаково для известного и неизвестного адреса.
- Роли и права лежат в базе: таблицы `Roles`, `RolePermissions`, внешний ключ `Users.roleId`. Роли `user`, `moderator`, `admin` создаются из модуля `src/permissions.js` (тест сравнивает базу с модулем), первый администратор берётся из `ADMIN_EMAIL` и `ADMIN_PASSWORD`. Нельзя выдать право, которого нет у вызывающего, удалить роль в использовании и снять роль с последнего администратора.
- Не сделано: отправка настоящей почты (только консоль и файл), проверка пароля по большой базе утёкших паролей, привязка сессии к устройству.
- Примеры: `curl -s -X POST http://localhost:3000/auth/refresh -H "Content-Type: application/json" -d '{"refreshToken":"<токен>"}'`, остальное в [`requests.http`](requests.http).
