# Часть 2. Лабораторная работа 3. Аутентификация и авторизация

Проект DSLKit (диаграммы как код, SaaS). Условие: `materials/text/part-2/Модуль 01…/38. Лабораторная работа 3…`. Работа продолжает [лабораторную работу 2](../lab-02-sequelize): добавлены пользователи, регистрация, вход с JWT, защита маршрутов и ролевая модель. Отчёты: [`report.md`](report.md) на русском, [`report.en.md`](report.en.md) на английском (шаблоны `report.tpl.md`, `report.en.tpl.md`; сборка `node tools/build.js part-2/lab-03-auth` из корня репозитория).

**Ветка для сдачи: `23`** (по условию). Она создана от ветки `lab12`, где лежат лабораторные работы 1 и 2.

## 1 Что сделано

| Метод           | Путь                         | Доступ             | Ответы                                                          |
| --------------- | ---------------------------- | ------------------ | --------------------------------------------------------------- |
| `POST`          | `/auth/register`             | все                | 201 пользователь без хеша, 400 неверные данные, 409 email занят |
| `POST`          | `/auth/login`                | все                | 200 `{ token, tokenType, expiresIn }`, 400, 401 неверная пара   |
| `GET`           | `/profile`                   | токен              | 200 текущий пользователь, 401                                   |
| `GET`           | `/diagrams`, `/diagrams/:id` | токен              | 200, 404                                                        |
| `POST`          | `/diagrams`                  | токен              | 201, владелец это вызывающий пользователь                       |
| `PUT`, `PATCH`, `DELETE` | `/diagrams/:id`     | владелец или admin | 200 или 204, 400, 403 чужая диаграмма, 404                      |
| `GET`           | `/users`                     | admin              | 200 список без хешей, 403                                       |
| `PATCH`         | `/users/:id/role`            | admin              | 200, 400 неверная роль или своя роль, 404                       |
| `DELETE`        | `/users/:id`                 | admin              | 204, 400 удаление себя, 404                                     |

**Дополнительный механизм: ролевая модель (RBAC).** Поле `role` (`user` или `admin`), middleware `requireRole('admin')`, маршруты управления пользователями и правило «менять и удалять диаграмму может владелец или admin». Роль при регистрации всегда `user`; первого администратора создаёт сид из переменных окружения.

## 2 Безопасность: решения

- Пароль хранится только как хеш bcrypt (10 раундов), длина пароля от 8 символов и не больше 72 байт (дальше bcrypt обрезает).
- Токен подписан HS256, срок жизни из `JWT_EXPIRES_IN` (по умолчанию 1 час). Проверка принимает только HS256, поэтому токены `alg: none` и HS512 отклоняются.
- После проверки подписи middleware читает пользователя из базы: удалённая учётная запись и смена роли действуют сразу, а `req.user` содержит `{ id, email, role }` из базы.
- Вход отвечает одинаково на неверный пароль и неизвестный email и тратит одинаковое время (сравнение с запасным хешем).
- Email приводится к нижнему регистру, дубликаты ловит уникальный индекс (ответ 409 и при гонке запросов).
- Секрет `JWT_SECRET` обязателен (от 32 символов), без него сервер не запускается. В репозитории только `.env.example`.
- Защита от перебора: 20 входов с адреса за 15 минут (ответ 429 и `Retry-After`), после 5 неудачных попыток почта блокируется на 15 минут, в том числе для неизвестных почт. Счётчики в памяти процесса. Срок токена не больше 24 часов, секрет от 32 символов, издатель `dslkit`, заголовки безопасности и журнал запросов в таблице `RequestLogs`. Пределы длины лежат в `limits.json`.
- Не реализовано: выход с отзывом токена, refresh-токены. Это описано в отчёте как ограничение.

## 3 Запуск

Нужен Node.js 22 или новее. SQLite используется по умолчанию, PostgreSQL и Neon подключаются так же, как в лабораторной работе 2 (`DATABASE_URL`).

```bash
cd part-2/lab-03-auth
npm install
cp .env.example .env     # затем задайте JWT_SECRET, при желании ADMIN_EMAIL и ADMIN_PASSWORD
npm run db:migrate
npm run db:seed          # демо-диаграммы и администратор (если заданы ADMIN_*)
npm run dev
npm test
```

Секрет можно сгенерировать командой `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`. Примеры запросов для расширения REST Client лежат в [`requests.http`](requests.http). Пример для curl:

```bash
curl -s -X POST http://localhost:3000/auth/login -H "Content-Type: application/json" \
  -d '{"email":"alice@example.com","password":"correct horse 42"}'
curl -s http://localhost:3000/profile -H "Authorization: Bearer <token>"
```

## 6 PUT и PATCH

`PUT /diagrams/:id` заменяет диаграмму целиком: нужны все обязательные поля, пропущенный `priority` получает значение по умолчанию. `PATCH /diagrams/:id` меняет только присланные поля (например `{"priority":"high"}`), остальные остаются прежними. Каждое присланное поле проверяется как в `POST`, пустое тело или тело без известных полей даёт 400, поле владельца прислать нельзя. Права те же, что у `PUT`: менять может владелец или admin, остальные получают 403. `PUT` идемпотентен, `PATCH` по определению не обязан быть таким.

## 7 Как вызвать ответ 500 настоящим сбоем

Ответ 500 вызывается сбоем базы, а не кнопкой.

- SQLite: запустите `npm start`, во втором окне выполните `npx sequelize-cli db:migrate:undo:all`. Таблицы исчезают под работающим сервером, первый же запрос не может записать строку в журнал `RequestLogs` и получает 500 с телом `{ "error": "Internal server error" }`, подробности остаются только в консоли сервера. Вернуть работу: `npm run db:migrate` и `npm run db:seed`.
- PostgreSQL (Neon, Supabase или локальный): остановите службу или контейнер базы, запросы дают 500, а `GET /health` отвечает 503.
- Запуск при недоступной базе завершается с кодом 1 и сообщением, сервер не поднимается.
