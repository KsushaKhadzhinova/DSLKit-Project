# Карточки к защите курсовой работы DSLKit

Каждая карточка: вопрос, короткий ответ (30–40 секунд вслух), где посмотреть в коде или записке. Ответы опираются на текст записки `note.md` и на код веток `25` (клиент и сервер) и `28` (Docker).

## Блок 1. О проекте

**1. Что за приложение и для кого оно?**
DSLKit хранит диаграммы, записанные текстом (UML, BPMN, ERD, DFD, IDEF0, сети Петри). Пользователь регистрируется, ведёт свои диаграммы, администратор управляет всеми записями и пользователями. Подходит студенческой группе или небольшой команде. Записка: введение, раздел 1.1.

**2. Какие есть роли и что каждая может?**
Гость: регистрация и вход. Пользователь: свои диаграммы и профиль. Администратор: всё то же плюс чужие диаграммы, список пользователей, смена роли, удаление пользователя без диаграмм. Рисунок 1, таблица 1 (FR1–FR12).

**3. Какие три модуля требует условие и где они?**
Аутентификация (`/auth/*`, `/profile`), диаграммы (CRUD `/diagrams`), администрирование (`/users`). Отмечены в последнем столбце таблицы 1.

**4. Чем курсовая отличается от лабораторных?**
Лабораторные дают отдельные части (сервер, база, клиент, Docker). В курсовой они собраны в одну систему с единой точкой входа, требованиями, тестами и руководством пользователя. Сервер из ЛР3, клиент из ЛР5, стек из ЛР8.

## Блок 2. Архитектура

**5. Как устроена система?**
Три контейнера: Nginx с собранным React, сервер Express, PostgreSQL. Браузер обращается только к Nginx на порту 8080, запросы `/api/` Nginx пересылает серверу, база доступна только серверу. Рисунки 2 и 3 (модель C4).

**6. Зачем единая точка входа через Nginx?**
Для браузера клиент и сервер на одном источнике, поэтому CORS в контейнерном режиме не нужен. Адрес сервера не вшит в сборку клиента, один образ работает в любом окружении.

**7. Почему CORS всё же настроен?**
В режиме разработки клиент (порт 5178) обращается к серверу (порт 3000) напрямую. Разрешён один адрес из настройки, значение `*` запрещено, ставится `Vary: Origin`.

**8. Почему REST, а не GraphQL?**
Ресурсов немного, операции стандартные (CRUD), статусы HTTP полностью описывают результат. REST проще тестировать и кэшировать, а в курсе он основной.

**9. Как устроены ошибки API?**
Всегда JSON `{ "error", "details" }`; `details` — список полей с проблемами. При 500 клиент получает только «Internal server error», трассировка остаётся в журнале сервера.

## Блок 3. База данных

**10. Какая база и почему?**
PostgreSQL 16: ограничения целостности, транзакции, привычный выбор для продакшена. SQLite используется только в тестах, чтобы они не требовали сервера. Подключение через `DATABASE_URL`.

**11. Какие таблицы?**
`Users` (почта в нижнем регистре, хеш, роль), `Diagrams` (название до 80 символов, нотация из списка, код до 10000, приоритет, владелец), `Comments` (текст до 1000 символов, диаграмма, автор), журнал запросов. Рисунок 4.

**12. Сколько сущностей и как связаны комментарии?**
Четыре: пользователи, диаграммы, комментарии, журнал запросов. Комментарий ссылается на диаграмму и на автора, оба ключа `CASCADE`: удалили диаграмму или пользователя, его комментарии ушли вместе с ним. Автора сервер берёт из токена, а не из тела запроса.

**13. Как защищена целостность на уровне базы?**
Проверки в самой таблице: допустимая нотация, непустое название без пробельных значений, предел длины. Запись в обход API не создаст некорректную строку.

**14. Что такое миграции и сиды?**
Миграции Sequelize версионируют схему и применяются при старте сервера. Сид создаёт первого администратора из переменных окружения.

## Блок 4. Безопасность

**15. Как хранятся пароли?**
Только хеш bcrypt (10 раундов; в тестах 4 для скорости). Длина пароля от 8 символов и не больше 72 байт — это предел bcrypt.

**16. Как работает JWT?**
Вход: сервер сверяет пароль с хешем и подписывает токен HS256 (издатель `dslkit`, срок 1 час, максимум 24). Клиент шлёт `Authorization: Bearer`. Сервер проверяет подпись, издатель и срок, затем загружает пользователя из базы.

**17. Почему роль берётся из базы, а не из токена?**
Роль в токене только подсказка. Если брать из токена, удаление пользователя и смена роли заработали бы лишь после истечения токена. По базе они действуют сразу.

**18. Что защищает от подбора пароля?**
Не больше 20 входов с адреса за 15 минут (ответ 429 и `Retry-After`), блокировка почты на 15 минут после 5 неудач, не больше 10 регистраций с адреса в час.

**19. Как скрыто, зарегистрирована ли почта?**
Ответ и время одинаковы для неверного пароля и неизвестной почты: для неизвестной почты сравнение идёт с запасным хешем.

**20. Как защищено от SQL-инъекций?**
Параметризованные запросы Sequelize, поле сортировки выбирается только из белого списка. Поиск по подстроке передаётся параметром.

**21. Почему не используется helmet?**
Нужные заголовки (политика содержимого, запрет фрейма, `nosniff`, запрет кэша) записаны вручную в `src/middleware/http.js` и покрыты тестами. Выбор осознанный: видно, что делает каждый заголовок. Можно заменить на helmet без изменения поведения.

**22. Что с XSS?**
React экранирует вывод; код диаграммы показывается как текст, это проверено тестом.

## Блок 5. Клиент

**23. Как устроен клиент и есть ли маршрутизация?**
React Router 6. Публичные `/login` и `/register`, защищённые `/diagrams` и `/diagrams/:id` (гость уходит на вход, после входа возвращается на запрошенный адрес, адрес проверяет `safeReturnPath`), ролевой `/admin` (обычный пользователь видит 403). Роль берётся с сервера запросом `/profile`. Скрытие страницы не защита, сервер проверяет каждый запрос.

**24. Как клиент работает с сервером?**
Через axios с перехватчиками: токен подставляется автоматически, ошибка 401 сбрасывает сессию, повтор запроса при сетевом сбое (3 попытки, пауза 300 мс). Тексты ошибок понятные.

**25. Что такое оптимистичное обновление?**
Хук `useDiagrams` сразу показывает новую запись, а при ошибке сервера откатывает её. Интерфейс не ждёт ответа.

**26. Как клиент и сервер согласуют ограничения ввода?**
Общий `limits.json` (длина названия, кода, почты, пароля). Изменение предела делается в одном месте.

**27. Как обеспечена адаптивность и доступность?**
Ширина от 375 до 1280 пикселей, цели нажатия от 44 пикселей, подписи полей, пропуск навигации, контраст по WCAG 2.2 AA.

## Блок 6. Docker, тесты, развёртывание

**28. Что делает Docker-стек?**
`docker compose up --build` поднимает базу, сервер, клиент. У каждого проверка работоспособности, порядок запуска через `service_healthy`, база во внутренней сети без публикации порта.

**29. Что сделано для безопасности контейнеров?**
Сервер от непривилегированного пользователя, `read_only`, `cap_drop: ALL`, `no-new-privileges`, лимиты памяти и процессов, двухэтапные образы, секреты только в `.env`.

**30. Какие тесты и какое покрытие?**
Сервер: 136 тестов `node --test`, покрытие строк 100%, ветвей 98%. Клиент: 100 тестов Vitest и Testing Library. Docker-конфигурация проверена тестами файлов. Таблица контрольных примеров в разделе 3.2.

**31. Где развёрнуто приложение?**
Честно: публичного адреса пока нет, основной способ запуска — Docker Compose на одной машине. Для публикации подходят Render, Supabase или Neon (приложение Е).

**32. Что бы вы улучшили?**
Облачный деплой, непрерывная интеграция в GitHub Actions, ответы на комментарии и обновление в реальном времени, отзыв токенов.
