# Тест-план DSLKit (веб-редактор диаграмм «как код»)

Структура плана следует разделу о тест-планировании в книге С. С. Куликова «Тестирование программного обеспечения. Базовый курс» (https://svyatoslav.biz/software_testing_book/): назначение, объект, что тестируем и что нет, стратегия, критерии начала и окончания, приостановка и возобновление, расписание, ресурсы, риски, метрики, артефакты. Правила пересказаны. Версия плана 1.0, дата 29.10.2026, ветка `testing-course-full`.

Связанные документы папки `docs/testing-kulikov/`: 01 требования, 02 варианты использования, 03 пользовательские сценарии, 11 чек-листы, 12 тест-дизайн, 13 тест-кейсы, 14 матрица трассировки. Прежние материалы (`testing-course/`, `docs/TESTING-BY-THE-BOOK.md`, `testing-course/documents/04-full-test-documentation.md`) не заменяются: они остаются отчётами о выполненных лабораторных, а этот комплект добавляет полный тест-дизайн и расширенный набор кейсов под новые функции (учётные записи, корзина, квота, шаблоны, собственное API).

## 1. Введение и цель

DSLKit это браузерный редактор, в котором диаграмму пишут текстом (DSL), а сайт рисует её в выбранной нотации (IDEF0/1/1X/3/4/5, DFD, ERD, BPMN, сети Петри, ГОСТ-блок-схемы, графы, DAG, диаграммы UML). Данные хранятся в браузере (`localStorage`), сервера учётных записей нет. Есть собственный HTTP-API отрисовки (`tools/render-api.js`).

Цель тестирования: показать, что экраны входа, регистрации, «Мои проекты» (с корзиной, шаблонами и квотой), редактора, настроек и API работают по требованиям, не теряют данные пользователя и не позволяют внедрить код через названия и DSL.

## 2. Объект тестирования

Сборка: рабочая копия ветки `testing-course-full`, сайт из `site/`, локальный сервер `npm start` (`tools/server.js`) на `http://localhost:5190`.

## 3. Что тестируем и что нет

Входит в объём:

1. Регистрация, вход, выход, защита страницы «Мои проекты» от гостя (редактор, настройки и welcome открыты гостю по REQ-021), раздельное хранение данных пользователей.
2. Жизненный цикл проекта: создание, автосохранение, переименование, корзина, восстановление, удаление навсегда, автоочистка через 30 дней, очистка корзины.
3. Квота (5 новых диаграмм в день), стартовые диаграммы, шаблоны, лайк и копирование, поиск, фильтр, сортировка.
4. Редактор: ввод DSL, проверка и панель проблем, отрисовка движком в браузере, экспорт, импорт, палитра, горячие клавиши, предупреждение о несохранённых изменениях.
5. Настройки и тема, язык ru/en.
6. API отрисовки: форматы запросов, коды ответов, предел 100000 символов.
7. Нефункциональные свойства: безопасность (XSS, очистка SVG, хранение пароля), производительность, доступность, адаптивность, кросс-браузерность, локализация, устойчивость к повреждённому хранилищу.

Не входит в объём (с причиной):

| Не тестируем                                                           | Причина                                                                                   |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Публичный сервис Kroki (движки Graphviz, Mermaid, PlantUML через сеть) | внешний сервис; проверяем только поведение DSLKit при его недоступности (офлайн, таймаут) |
| Настоящая серверная аутентификация                                     | её нет: учётные записи живут в браузере (ограничение зафиксировано как риск R-05)         |
| Нагрузочное тестирование с тысячами пользователей                      | нет серверной части, одна вкладка одного браузера                                         |
| Печатные макеты, почтовые рассылки                                     | функций нет                                                                               |
| Платёжные функции                                                      | отсутствуют                                                                               |

## 4. Стратегия тестирования

Подход смешанный: ручное тестирование по тест-кейсам и чек-листам плюс автоматизация там, где она уже есть (модульные тесты `labs/05-javascript-interactivity`, e2e-сценарии `testing-course/full/*.py` на Playwright, скрипт `static-sec-perf.js`).

Порядок работ (идея книги: от простого к сложному, от широкого к глубокому):

1. Дымовой тест сборки: сервер отвечает, все шесть страниц `/app/*` открываются, консоль без ошибок.
2. Тест критического пути: регистрация, создание диаграммы, сохранение, выход, вход, диаграмма на месте.
3. Расширенное тестирование по тест-кейсам (документ 13), техники из документа 12.
4. Исследовательское тестирование сессиями по 45 минут с чартером (раздел 8 этого плана).
5. Регрессия после каждого исправления дефекта: повторяется кейс, нашедший дефект, плюс связанные по матрице (документ 14).

Приоритизация по книге: важность кейса задаётся по риску (A/B/C: высокая, средняя, низкая). В документе 13 им соответствуют `High`, `Medium`, `Low`.

Уровни: модульный (разработчик), интеграционный (взаимодействие хранилища и интерфейса), системный (этот план), приёмочный (по Use Case владельца продукта).

Виды тестирования:

| Вид                  | Что проверяем                                                                                                              | Основной инструмент                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| Функциональное       | требования REQ-001…REQ-123 из 01-requirements.md                                                                           | ручные кейсы, e2e                     |
| UI                   | раскладка, состояния кнопок, подсказки, фокус, тёмная и светлая темы                                                       | ручная проверка, скриншоты            |
| Кросс-браузерное     | Chrome и Edge (Chromium), Firefox, Safari (WebKit) последние две версии                                                    | Playwright, ручная проверка           |
| Адаптивность         | ширина 320, 375, 768, 1024, 1366, 1920 px; поворот экрана                                                                  | эмуляция в DevTools                   |
| Безопасность         | XSS в названиях, DSL, импорте; очистка SVG; хэш пароля; одинаковый ответ на неверную почту и пароль; заголовки ответов API | ручные кейсы, `static-sec-perf.js`    |
| Производительность   | загрузка страницы, отрисовка большой диаграммы, ответ API на 100000 символов                                               | Lighthouse, замеры в DevTools         |
| Доступность          | клавиатура, `aria-*`, контраст, программы чтения, `prefers-reduced-motion`                                                 | axe, ручная проверка                  |
| Локализация          | ru и en: тексты, формат даты, правильные формы чисел                                                                       | ручная проверка двух версий           |
| API                  | коды, формат ошибок, граничные размеры, методы, типы содержимого                                                           | curl, Node `fetch`, Postman           |
| Устойчивость         | повреждённое или переполненное хранилище, две вкладки, офлайн                                                              | ручные кейсы с правкой `localStorage` |
| Совместимость данных | старые ключи хранилища без `created`, без `trashedAt`                                                                      | ручные кейсы                          |

## 5. Критерии начала тестирования (входные)

1. Сборка ветки открывается на `http://localhost:5190`, `npm test` в корне даёт 0 упавших тестов.
2. Все требования из `01-requirements.md` имеют идентификаторы REQ-xxx и согласованы с владельцем продукта; открытые вопросы перечислены в разделе 6 документа 14.
3. Тестовые данные подготовлены: пустой профиль браузера, три тестовые учётные записи (значения хранятся в `testing-course/` и не используются вне тестов), набор DSL из документа 12.
4. Установлены браузеры из таблицы видов тестирования.

## 6. Критерии окончания тестирования (выходные)

1. Выполнены 100 % кейсов приоритета High и не менее 90 % кейсов Medium и Low.
2. Нет открытых дефектов с важностью Критическая или Высокая; для Средней допустимо не более 3 с согласованным обходом.
3. Покрытие требований тест-кейсами по матрице 100 %, покрытие переходов диаграммы состояний проекта 100 %.
4. Дымовой тест и тест критического пути проходят в трёх браузерах.
5. Отчёт о тестировании выпущен (метрики раздела 11).

## 7. Критерии приостановки и возобновления

Приостанавливаем, если: не открывается сервер или любая страница `/app/*` (блокирующий дефект), падает дымовой тест, хранилище браузера недоступно во всех тестовых профилях, обнаружена утечка данных между учётными записями (останавливаем все функциональные проверки, пока дефект не исправлен). Возобновляем после выпуска исправления и повторного успешного дымового теста.

## 11. Метрики и отчётность

По книге собираем: число выполненных, пройденных, проваленных и заблокированных кейсов; покрытие требований; покрытие переходов; плотность дефектов (дефектов на модуль); процент дефектов по важности и срочности; скорость выполнения (кейсов в час). Формулы: покрытие требований = требования с хотя бы одним кейсом / все требования; пройдено % = пройденные / выполненные.

Отчёт о дефекте оформляется по полям книги: идентификатор, краткое описание, подробное описание, шаги, фактический и ожидаемый результат, окружение, важность, срочность, симптом, возможность обойти, автор, дата, вложения (скриншот, HAR, значения `localStorage`).

Шкалы: важность Критическая, Высокая, Средняя, Низкая, Косметическая; срочность Немедленно, Высокая, Обычная, Низкая.
