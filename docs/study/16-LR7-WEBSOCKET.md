# ЛР7. WebSocket и Socket.IO: разбор для защиты

Ветка `27`, папка `part-2/lab-07-websocket`. Английская версия: `16-LR7-WEBSOCKET.en.md`. Запуск описан в `00-RUN-GUIDE.md`. Это сервер Express и Socket.IO с клиентом на чистом JavaScript: комната на каждую диаграмму, кто сейчас в ней, кто редактирует, кто печатает, чат и личные сообщения. Здесь только то, что нужно понимать и уметь дописать при преподавателе.

## 1 Что делает работа за одну минуту

Пользователь входит под именем (получает подписанный токен), подключается к серверу по WebSocket и входит в комнаты по названию диаграммы. В комнате он видит список участников, отметки «редактирует» и «печатает», историю последних 50 сообщений и общий чат. Есть личные сообщения по идентификатору сокета. История хранится в памяти, а при заданной `MONGODB_URI` в MongoDB и переживает перезапуск.

HTTP-часть маленькая: статический клиент, `POST /login`, `GET /health`, `GET /limits.json`, страницы 404 и 500.

| Событие клиента | Данные | Ответ (подтверждение) |
| --- | --- | --- |
| `room:join` | `{ room }` | `{ ok, room, history, users }` |
| `room:leave` | `{ room }` | `{ ok }` |
| `chat:message` | `{ room, text }` | `{ ok, id }` |
| `private:message` | `{ to, text }` | `{ ok, message }` |
| `typing` | `{ room, typing }` | нет |
| `editing` | `{ room, editing }` | `{ ok, editing }` |

События сервера: `welcome`, `user:online`, `user:offline`, `room:joined`, `room:left`, `presence:update`, `chat:message`, `private:message`, `typing`.

## 2 Как устроен проект

```
server.js                      запуск; с MONGODB_URI подключает историю в MongoDB
src/app.js                     Express, заголовки, /login, /health, 404/500, Socket.IO
src/socket.js                  все события: createHub, handshake, комнаты, сообщения
src/validate.js                очистка имени, комнаты и текста
src/token.js                   подписанный токен входа (HMAC-SHA256)
src/origin.js                  проверка Origin при подключении
src/rate-limit.js              ограничитель частоты событий
src/history.js                 история: память или MongoDB (один интерфейс add/list)
limits.json                    все пределы
public/                        клиент: index.html, client.js, стили, 404/500
```

Принцип: серверная логика разделена на небольшие функции (`createHandshake`, `createRoomActions`, `createMessageActions`), история подключается через интерфейс `add` и `list`, поэтому замена памяти на MongoDB не трогает обработчики.

## 3 Жизнь соединения

```mermaid
sequenceDiagram
  participant B as Браузер
  participant H as HTTP (Express)
  participant S as Socket.IO
  B->>H: POST /login { username }
  H-->>B: { token }
  B->>S: подключение, auth.token
  S->>S: allowRequest: Origin; handshake: токен, имя, лимиты
  S-->>B: welcome { id, username, online }
  S-->>B: user:online всем остальным
  B->>S: room:join { room } (с подтверждением)
  S->>S: history.list(room)
  S-->>B: ack { history, users }
  S-->>B: presence:update всем в комнате
  B->>S: chat:message { room, text }
  S->>S: проверка, лимит, history.add
  S-->>B: io.to(room) chat:message всем в комнате
  B->>S: обрыв
  S-->>B: disconnect: выйти из комнат, user:offline
```

## 4 Разбор главного

### Подключение и защита (`createHandshake`, `origin.js`)
- `allowRequest` проверяет заголовок `Origin`: браузер всегда присылает его при подключении, и страница с чужого сайта не может открыть сокет от имени посетителя (межсайтовый перехват WebSocket). Запросы без `Origin` (не браузер) пропускаются.
- Имя берётся из подписанного токена `auth.token`; без токена допустимо `auth.username`, если не включён `REQUIRE_TOKEN=1`. Токен подписан HMAC-SHA256 и проверяется сравнением за постоянное время (`timingSafeEqual`); в нём имя и срок действия. Это упрощённый токен для работы, настоящая служба использовала бы JWT (как в ЛР3).
- Имя проверяется (`cleanName`: буквы, цифры, точка, дефис, подчёркивание, до 24 знаков), должно быть свободно, а число пользователей и число подключений с одного адреса ограничены.
- Отказ в `io.use` приходит клиенту событием `connect_error`.

### Комнаты и присутствие (`createRoomActions`)
- Комната это именованная группа сокетов: `socket.join(room)`, `io.to(room).emit(...)`. Название приводится к нижнему регистру и проверяется регулярным выражением.
- Сервер отдельно ведёт `rooms: Map<комната, Map<сокет, пользователь>>`, поэтому список «кто в комнате» строится без запросов.
- Пределы: пять комнат на пользователя, 50 участников в комнате. Пустая комната удаляется из таблицы.
- `editing` ставит пользователю отметку «редактирует»; `typing` рассылается всем в комнате, кроме отправившего (`socket.to(room)`).

### Сообщения (`createMessageActions`)
- Текст чистится (`cleanText`): скрытые управляющие символы и символы смены направления текста вырезаются, пробельное значение отвергается, длина не больше 500.
- Отправитель всегда берётся из соединения, а не из присланных данных, поэтому подделать «от кого» нельзя.
- В комнату: `io.to(room).emit('chat:message', message)` получают все, включая отправителя; в личное: `target.emit('private:message', ...)` получает только адресат, а отправитель видит копию из подтверждения.
- Подтверждение (`ack`) это последний аргумент события; сервер вызывает его функцией `succeed` или `fail`. Для каждого события есть проверка, что `ack` вообще функция.

### Ограничение нагрузки
Два ограничителя: чат не чаще 5 сообщений за 2 секунды, любые события не чаще 40 за 2 секунды. Размер пакета ограничен `maxHttpBufferSize` (10000 байт), поэтому огромное сообщение закрывает соединение. Обработчики одного сокета выполняются по очереди (`tail = tail.then(...)`), чтобы выход из комнаты сразу после входа дожидался загрузки истории.

### История
`createHistory` держит по списку на комнату в памяти (последние 50, не более 200 комнат). `createMongoHistory` пишет документ `{ ...message, room }` и читает 50 последних по `_id`, отдавая клиенту по возрастанию. Если база недоступна, вход в комнату и отправка отвечают понятной ошибкой через `ack`.

### Отключение
На `disconnect` пользователь выходит из всех комнат (с рассылкой `room:left` и обновлением списка), удаляется из онлайн-списка и счётчика адресов, остальным уходит `user:offline`. Данных на отключённый сокет не остаётся.

### Клиент (`public/client.js`)
Текст сообщений вставляется как текст, а не как разметка (защита от внедрения кода), политика CSP запрещает встроенные скрипты. При восстановлении соединения клиент заново входит в свои комнаты (`connect`).

## 5 Вопросы, которые вероятны на защите

В условии 16 вопросов; для варианта 26 это 9–11 (n−1, n, n+1 при n=10). Развёрнутые ответы в отчёте, раздел 3.7.

- **Как отправить приватное сообщение конкретному пользователю (9).** По идентификатору сокета: `io.sockets.sockets.get(id).emit(...)` или `io.to(id).emit(...)`, потому что каждый сокет автоматически состоит в комнате со своим id. В работе это событие `private:message`.
- **Как реализовать подтверждение получения (10).** Последним аргументом `emit` передаётся функция; сервер вызывает её, клиент получает результат. В работе так отвечают все события, кроме `typing`.
- **Как масштабировать на несколько серверов (11).** Нужен адаптер (Redis adapter): он пересылает события между процессами, а балансировщик должен держать клиента на одном сервере (sticky sessions) для длинного опроса. История в MongoDB уже общая; таблицы онлайн-пользователей в памяти пришлось бы вынести.
- **Чем WebSocket отличается от HTTP.** Одно постоянное двустороннее соединение вместо цикла запрос-ответ; сервер может писать первым.
- **`socket.emit`, `io.emit`, `socket.broadcast.emit` (16).** Первое только этому сокету, второе всем, третье всем, кроме этого сокета; для комнат `io.to(room)` и `socket.to(room)` (без отправителя).
- **Как защитить от неавторизованного подключения (14).** Токен в `auth`, проверка `Origin`, лимиты подключений, очистка имён.
- **Что происходит при потере связи (12).** Клиент получает `disconnect`, затем `reconnect_attempt` у менеджера, при удаче `connect` (вход в комнаты повторяют вручную). `connectionStateRecovery` не включён.
- **Как сделать паузу при медленном соединении (15).** Не реализовано; ответ: подтверждения как окно, `socket.volatile.emit` для необязательных событий, проверка `socket.conn.writeBuffer.length`.

## 6 Допиши при мне: тренировка

1. **Событие «прочитано».** Новое событие `chat:read` с проверкой комнаты, рассылка `socket.to(room).emit('chat:read', ...)`, подтверждение через `succeed`.
2. **Комната «только для чтения».** В `toRoom` проверить список запретов до `history.add`.
3. **Удалить своё сообщение.** Событие с идентификатором, проверка автора по `message.fromId`, `io.to(room).emit('chat:deleted', ...)`; в хранилище метод `remove`.
4. **Команда `/me` в тексте.** В `toRoom` распознать префикс и пометить `message.action = true`.
5. **Таблица различий `emit`.** Держать наготове три строки в разных обработчиках: `socket.emit`, `socket.broadcast.emit`, `io.to(room).emit`.
6. **Флуд.** Из консоли отправить 50 сообщений подряд и показать «Too many messages».

## 7 Что проверить руками перед защитой

```bash
npm install
npm test
npm start
```

Откройте две вкладки на `http://localhost:3000`, войдите под разными именами, войдите в одну комнату: видны оба участника, сообщения приходят в обе вкладки, «печатает» и «редактирует» видны у другого. Попробуйте занятое имя (ошибка), 501 символ из консоли браузера (`socket.emit`), личное сообщение по идентификатору. Для истории в MongoDB задайте `MONGODB_URI` в `.env` (в чат и коммиты не переносить) и перезапустите сервер: история должна остаться. Скриншоты для отчёта уже в папке `figures`.
