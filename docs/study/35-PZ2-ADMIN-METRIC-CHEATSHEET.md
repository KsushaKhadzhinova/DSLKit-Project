# ПЗ2: шпаргалка «добавить новую метрику для администратора» и сбой журнала

Английская версия: `35-PZ2-ADMIN-METRIC-CHEATSHEET.en.md`. Работа: `part-2/pz-02-rest-api`, ветка `pz22`.

## Как устроен журнал

Файл `src/journal.js`. Таблица `request_log` (SQLite, файл из `JOURNAL_FILE`, по умолчанию `journal.sqlite`): `id`, `created_at`, `method`, `path`, `ip`, `status`. Промежуточный обработчик `journaling` стоит в `src/app.js` сразу после ограничителя частоты и **до** разбора тела и маршрутов:

1. запрос записывается в таблицу (`journal.begin`), статус пока пуст;
2. если запись не удалась, ответ 500 `journal_unavailable` в едином формате, **маршрут не выполняется**, ошибка пишется в консоль;
3. иначе запрос идёт дальше, а по событию `finish` в строку дописывается код ответа (`journal.finish`); сбой этой записи только пишется в консоль (ответ уже отправлен).

Правило преподавателя: при сбое журнала работа без него запрещена, молча продолжать нельзя. Поэтому запись идёт раньше действия. Данные ресурсов лежат в массиве (условие ПЗ2), откатывать нечего: действие просто не начинается.

## Как воспроизвести сбой

- Тест: `node --test test/journal.test.js` (сбой записи, закрытая база, сбой записи статуса).
- Руками: запустить сервер, остановить его, сделать файл журнала доступным только для чтения (`attrib +R journal.sqlite`), запустить снова; любой запрос к `/api/...` отвечает 500 `journal_unavailable`, `GET /health` остаётся 200. Вернуть: `attrib -R journal.sqlite`.
- Если файл вообще нельзя открыть (`JOURNAL_FILE=Z:/нет/папки/j.sqlite`), сервер не стартует.

## Допзадание: добавить метрику (пример: время обработки в миллисекундах)

1. **Таблица** (`src/journal.js`): в `CREATE TABLE` добавить `duration_ms INTEGER`. Для уже существующего файла добавить миграцию `ALTER TABLE request_log ADD COLUMN duration_ms INTEGER` в `try`, который игнорирует «duplicate column».
2. **Запись** (`journaling`): запомнить `const started = performance.now()` и в `res.on('finish')` передать `Math.round(performance.now() - started)` в `journal.finish(id, status, ms)`; в `finish` добавить `duration_ms = ?` в `UPDATE`.
3. **Чтение для администратора**: добавить поле в `SELECT` у `recent` и вывести его (маршрут `GET /api/journal`, закрытый токеном из `.env`, либо просто `console.table(journal.recent())`).
4. **Сбой**: если метрика считается при записи (в `begin`) и она упала, запрос получает 500 и не выполняется; поэтому метрики, известные заранее (метод, путь, адрес), пишутся в `begin`, а вычисляемые после ответа (время) в `finish`.
5. **Тест**: в `test/journal.test.js` проверить, что строка содержит новое поле, и что при броске из `begin` ответ 500.

## Вероятные вопросы

- Почему журнал пишется до выполнения? Чтобы при сбое журнала действие не выполнялось (работа без журнала запрещена).
- Почему `/health` не журналируется? Это проба живости; её отказ журнала не должен ронять.
- Почему 500, а не 503? Сбой записи это внутренняя ошибка сервера; код единый для всех сбоев журнала.
- Что с запросами, которые отклонил ограничитель частоты (429)? Они не журналируются: ограничитель стоит раньше, чтобы флуд не нагружал базу.
- Почему SQLite? Нужна таблица БД без отдельного сервера; для PostgreSQL заменяется один файл `src/journal.js` (те же три функции).
