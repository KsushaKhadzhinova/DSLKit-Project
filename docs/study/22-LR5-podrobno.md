## 3. Теория подробно

### 3.1. Клиент и сервер: «официант и кухня»

Браузер (клиент) это официант: принимает заказ у пользователя и несёт на кухню (сервер). Кухня готовит и возвращает ответ со статусом: «готово» (200), «создано» (201), «такого блюда нет» (404), «вы не представились» (401), «вам нельзя» (403), «на кухне пожар» (500). Между ними не прямая связь, а запрос-ответ по HTTP.

### 3.2. Почему `axios`, а не `fetch`

| | `fetch` | `axios` |
| --- | --- | --- |
| Ошибка на 4xx и 5xx | Не бросает: нужно проверять `response.ok` | Бросает исключение сам |
| JSON | `response.json()` вручную, `JSON.stringify` для тела | Автоматически |
| Перехватчики | Нет, нужна обёртка | Есть |
| Таймаут | Через `AbortController` | Параметр `timeout` |
| Размер | Встроен | Отдельная библиотека |

### 3.3. Токен: «пропуск, который показывают на каждой двери»

После входа сервер выдаёт JWT. Клиент сохраняет его и прикладывает к каждому запросу в заголовке `Authorization: Bearer ...`. Делать это в каждом вызове утомительно, поэтому используют **перехватчик запроса**: одна функция добавляет заголовок ко всем запросам. **Перехватчик ответа** смотрит на статус 401: если токен истёк, он удаляет токен и сообщает приложению «выйди из аккаунта».

Компромисс: токен в `localStorage` удобен (переживает перезагрузку), но его может прочитать любой скрипт на странице. Поэтому текст ошибок сервера React выводит как простой текст, а не как HTML.

### 3.4. Оптимистичное обновление: «забронировать, не дожидаясь подтверждения»

Обычный подход: нажал «Добавить» → крутится индикатор → пришёл ответ → запись появилась. Оптимистичный: запись появляется **сразу** (с временным id и пометкой «Сохраняется…»), параллельно уходит запрос. Если сервер ответил успехом, временная запись заменяется настоящей (с реальным id). Если отказал, запись убирается и показывается уведомление. Так пользователь не ждёт, а ошибка всё равно обрабатывается честно.

Для удаления: убрать из списка сразу, при отказе вернуть **на прежнее место** (запоминаем индекс). Для правки: применить сразу, при отказе вернуть старую запись.

### 3.5. Отмена запроса: «забрать заказ, если гость ушёл»

Пользователь набрал «а», потом «ав». Уйдут два запроса. Если ответ на первый придёт позже второго, он перетрёт результат (гонка). Решение: перед новым запросом **отменить** предыдущий через `AbortController`. Функция очистки `useEffect` вызывает `controller.abort()`: так же отменяется запрос, когда компонент удаляется с экрана.

### 3.6. Debounce в поиске

Тот же принцип, что в ЛР4: значение «осядет» только после паузы 400 мс. Хук `useDebouncedValue` отдаёт значение с задержкой, а запрос реагирует на задержанное значение, поэтому на каждую букву запрос не уходит.

### 3.7. Пагинация и `X-Total-Count`

Сервер отдаёт страницу (`limit=20&offset=0`) и в заголовке сообщает общее число записей. Клиент знает, сколько загрузил (`fetched`), и показывает «Загрузить ещё», пока `fetched < total`. Следующая страница запрашивается со смещением `offset = fetched`. Браузер по умолчанию не показывает JS нестандартные заголовки ответа, поэтому сервер добавляет `Access-Control-Expose-Headers: X-Total-Count`.

### 3.8. Повтор запросов (retry)

Чтение безопасно повторять (результат тот же). Повторяем, если сеть оборвалась или сервер ответил 5xx, до 3 попыток с растущей паузой (300, 600 мс). Не повторяем 4xx (повтор даст то же) и отменённые запросы. **Запись** (POST) не повторяем автоматически: можно создать дубль.

### 3.9. CORS: «охранник на входе чужого здания»

Клиент (`localhost:5178`) и сервер (`localhost:3000`) это разные «источники». Браузер по умолчанию не даёт странице читать ответ чужого источника. Сервер должен прислать `Access-Control-Allow-Origin` со значением адреса клиента. Для запросов с `Authorization` и JSON браузер сначала шлёт `OPTIONS` (preflight), и сервер отвечает, какие методы и заголовки разрешены. Звёздочка `*` у нас запрещена: разрешён ровно один адрес.

## 6. Вопросы преподавателя (вариант 26: вопросы 9, 10, 11)

### Вопрос 9. Как добавить Authorization header (Bearer token) к каждому запросу в axios с помощью interceptors?

**Ответ.** Interceptor это функция, которую axios вызывает автоматически. Для запросов её регистрируют через `api.interceptors.request.use(fn)`. Функция получает объект `config` запроса, добавляет заголовок и **обязательно возвращает** `config`:

```js
api.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});
```

Так заголовок прикладывается ко всем запросам этого экземпляра, и в компонентах токен не упоминается. Токен читается на каждом запросе, поэтому после входа или выхода ничего пересоздавать не нужно. Слово `Bearer` (и пробел) часть схемы: сервер ждёт именно такую форму.

**Из проекта:** `api.js`, строки 32–36 (то же самое с обёрткой `getToken` в `try/catch`). Плюс перехватчик ответа (39–48): на 401 при сохранённом токене токен удаляется и посылается событие `auth:logout`.

### Вопрос 10. Что такое дебаунс (debounce) и как он применяется для поискового ввода? Приведите пример.

**Ответ.** Debounce это приём «выполнить действие, только когда события перестали приходить на заданное время». Без него поиск отправлял бы запрос на **каждую** набранную букву: десятки лишних запросов и гонка ответов. С debounce запрос уходит, когда пользователь сделал паузу (у нас 400 мс). Каждое новое нажатие сбрасывает таймер.

Пример на хуке:

```js
function useDebouncedValue(value, delayMs) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(timer); // новое значение отменяет прежний таймер
  }, [value, delayMs]);
  return debounced;
}
// const debouncedSearch = useDebouncedValue(search, 400); запрос зависит от debouncedSearch
```

Отличие от throttle: throttle пропускает действие не чаще раза в N мс, debounce ждёт тишины.

**Из проекта:** `useDebouncedValue.js` (строки 4–11) и `DiagramsScreen.jsx` (строка 16): `useDebouncedValue(search.trim(), limits.searchDebounceMs)`, где `searchDebounceMs = 400`. Поле `SearchField` меняет `search` сразу (ввод не тормозит), а `useDiagrams` получает уже задержанное значение.

### Вопрос 11. Как отменить запрос при размонтировании компонента в useEffect с помощью AbortController?

**Ответ.** В эффекте создают `AbortController`, его `signal` передают в запрос, а в функции очистки вызывают `controller.abort()`. Очистка срабатывает при размонтировании и перед повторным запуском эффекта:

```js
useEffect(() => {
  const controller = new AbortController();
  axios.get(url, { signal: controller.signal })
    .then(setData)
    .catch((e) => { if (!axios.isCancel(e)) setError(e); });
  return () => controller.abort();
}, [url]);
```

Отмена даёт два эффекта: ответ не попадает в состояние уже удалённого компонента и ответ на устаревший запрос не затирает новый. Отменённый запрос завершается ошибкой особого вида, её нужно отличать от настоящей (`axios.isCancel`).

**Из проекта:** `useDiagrams.js`, строки 56 (создание), 62 (передача `signal`), 76 (отмена не считается ошибкой: `!isCanceled(failure)`), 84 (`controller.abort()` в очистке, плюс отмена загрузки следующей страницы `moreController`). Дополнительно `controller.signal.aborted` проверяется в `.then` и `.finally`.

## 7. Частые ошибки

1. **Забыть CORS.** Запрос с `localhost:5178` на `localhost:3000` блокируется браузером; в консоли «blocked by CORS policy». Нужен `cors` на сервере и точный адрес клиента (`CORS_ORIGIN`).
2. **Не открыть заголовок `X-Total-Count`.** Без `Access-Control-Expose-Headers` JS его не прочитает, «Загрузить ещё» не появится.
3. **Неверный `VITE_API_URL` или перезапуск без пересборки.** Переменные `VITE_*` читаются при старте dev-сервера: после правки `.env` нужно перезапустить `npm run dev`. Адрес задания `/api` не совпадает с нашим сервером (без `/api`).
4. **Не вернуть `config` из перехватчика.** Тогда запрос уйдёт «в пустоту».
5. **Считать 401 при входе «истёкшей сессией».** Поэтому проверка `getToken()` в перехватчике ответа.
6. **Игнорировать откат.** Оптимистичное обновление без обработки ошибки оставит на экране то, чего нет на сервере.
7. **Забыть про гонку запросов.** Без `AbortController` ответ на старый поиск может появиться после нового.
8. **Не проверять форму ответа.** Если вместо массива пришёл HTML (прокси, неверный адрес), `items.map` упадёт. Проверка `Array.isArray` (строка 66).
9. **Дублировать записи при «Загрузить ещё».** Дописывать страницу нужно с фильтром по уже известным `id` (строки 106–108).
10. **Автоповтор POST.** Создаст дубли; повторяют только чтение.
11. **Показывать текст ошибки сервера как HTML.** Выводить только как текст (XSS), особенно раз токен лежит в `localStorage`.
12. **Не закрыть `useEffect` очисткой.** Остаются таймеры и запросы после ухода со страницы.
13. **Запускать клиент без сервера ЛР3 из ветки `25`.** В ветке `23` нет CORS для этого клиента.

Проверка перед защитой: поднять PostgreSQL и сервер ЛР3 (`npm start` в `part-2/lab-03-auth`), запустить клиент (`npm run dev`), зарегистрироваться, добавить, изменить, удалить диаграмму, проверить поиск, «Загрузить ещё», остановить сервер и увидеть ошибку с «Повторить».
