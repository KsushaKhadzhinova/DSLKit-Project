## 3. Теория подробно

### 3.1. Реляционная и документная модели: «картотека» и «папка с вложениями»

Реляционная база (PostgreSQL) похожа на картотеку: диаграммы в одном ящике-таблице, комментарии в другом, а связывает их номер (внешний ключ). Чтобы показать диаграмму с комментариями, нужно «достать из двух ящиков и сопоставить» (JOIN).

Документная база (MongoDB) похожа на папку: диаграмма хранится одним документом, и **комментарии лежат внутри**:

```json
{
  "_id": "64b7f0c2a1b2c3d4e5f60718",
  "title": "Схема оплаты",
  "notation": "BPMN",
  "tags": ["shop", "payment"],
  "comments": [
    { "_id": "…", "author": "boris", "text": "Добавить возврат", "createdAt": "…" }
  ]
}
```

| | PostgreSQL (SQL) | MongoDB (NoSQL) |
| --- | --- | --- |
| Единица данных | строка таблицы | документ в коллекции |
| Схема | жёсткая, задаётся в БД | гибкая, в Mongoose задаёт приложение |
| Связи | внешние ключи и JOIN | вложение или ссылки (`ObjectId`, `populate`) |
| Запросы | SQL | методы и операторы (`find`, `$set`, `$push`) |
| Идентификатор | число или UUID | `ObjectId` |
| Транзакции | сильные по умолчанию | на одном документе атомарны; многодокументные отдельно |
| Плюс | целостность связей, сложные выборки | быстрое чтение вложенных данных, гибкость |
| Минус | JOIN дорогие, схему трудно менять | дублирование, документ растёт (предел 16 МБ) |

**Для DSLKit:** диаграмма с комментариями и тегами читается целиком одним запросом, поэтому документная модель удобна. Реляционная лучше для связей «многие ко многим», строгой целостности и отчётов.

### 3.2. Mongoose: «паспортный стол» для документов

MongoDB сама не требует от документа никакой формы. Mongoose добавляет «паспортный стол»: схема описывает поля, типы и правила (обязательное, длина, допустимые значения), модель даёт методы работы. Документ, не подходящий под схему, не сохранится (ошибка валидации).

### 3.3. Запросы: операторы с `$`

Фильтр это объект: `{ owner: 'anna' }`. Операторы начинаются с `$`:

- `$set` задать поля; `$push` добавить в массив; `$pull` убрать из массива;
- `$in`, `$all` проверить массив; `$exists` есть ли поле; `$gt`, `$gte` больше;
- `{ tags: 'shop' }` для поля-массива означает «массив **содержит** значение»;
- `{ 'comments.author': 'boris' }` точечный путь к вложенному полю;
- `$text` полнотекстовый поиск (нужен текстовый индекс).

### 3.4. Aggregation pipeline: «конвейер на заводе»

Данные едут по ленте. На каждой станции (стадии) с ними что-то делают: отобрать (`$match`), сгруппировать (`$group`), переименовать поля (`$project`), упорядочить (`$sort`). Выход одной стадии это вход следующей. Наш `stats` группирует диаграммы по нотации и считает количество, средний приоритет и число комментариев.

### 3.5. Индексы: «оглавление книги»

Без индекса MongoDB просматривает все документы (как читать книгу целиком в поисках слова). Индекс это оглавление: по нему поле находится быстро. Цена: места больше, запись медленнее, потому что индекс обновляется при каждой записи. Поэтому индексируют то, по чему часто ищут.

### 3.6. Вложенные документы: плюсы и минусы

Плюсы: чтение одним запросом, атомарность записи одного документа, нет JOIN. Минусы: документ растёт (поэтому у нас предел 100 комментариев и 20 тегов), данные дублируются, вложенные данные трудно использовать отдельно от родителя, предел размера документа 16 МБ.

### 3.7. Защита от NoSQL-инъекций

Если принимать из запроса объект как есть, злоумышленник пришлёт `{"owner": {"$ne": null}}` и получит все записи. Защита: проверять тип входных данных (строки), включить `sanitizeFilter`, проверять идентификаторы как `ObjectId` (24 шестнадцатеричных символа), отвергать неизвестные параметры.

## 6. Вопросы преподавателя (вариант 26: вопросы 9, 10, 11)

### Вопрос 9. Как в Mongoose создать индекс для поля (например, для ускорения поиска по email)?

**Ответ.** Два способа. Первый: параметр `index: true` в описании поля. Второй: метод схемы `schema.index({ поле: 1 })`, где `1` по возрастанию, `-1` по убыванию. Для уникальности `unique: true`. Составной индекс: `schema.index({ owner: 1, createdAt: -1 })`. Текстовый: `schema.index({ title: 'text' })`.

```js
const userSchema = new mongoose.Schema({
  email: { type: String, required: true, unique: true, index: true },
});
// или так:
userSchema.index({ email: 1 }, { unique: true });
```

Зачем: без индекса MongoDB просматривает все документы коллекции; с индексом по email находит нужный сразу. Цена: индекс занимает память и замедляет запись (его нужно обновлять), поэтому индексируют только поля, по которым часто ищут. Mongoose создаёт индексы автоматически при запуске приложения (`autoIndex`), на большой базе это отключают и создают индексы отдельно. Проверить использование индекса: `.explain()`.

**Из проекта:** `diagram.js`, строка 39 (`owner` с `index: true`), строка 42 (`tags` с `index: true`), строка 51 (индекс по вложенному полю массива `comments.author`, multikey), строка 54 (текстовый индекс `title` и `sourceCode`), `request-log.js`, строка 15 (индекс по `createdAt` с `expireAfterSeconds`, то есть TTL).

### Вопрос 10. Что такое populate в Mongoose и для чего он нужен? (если ссылаетесь на другую коллекцию)

**Ответ.** В MongoDB связь между коллекциями можно хранить ссылкой: поле с `ObjectId` другого документа. В схеме это записывают как `{ type: mongoose.Schema.Types.ObjectId, ref: 'User' }`. При чтении в таком поле лежит только идентификатор. `populate` **заменяет идентификатор самим документом** из указанной коллекции: `Diagram.find().populate('owner')`. Это аналог JOIN в SQL, но выполняется драйвером двумя запросами (не одним на стороне базы), поэтому злоупотреблять им не стоит. Можно выбрать поля: `populate('owner', 'name email')`.

Когда нужен: когда данные нельзя вложить (они большие, общие для многих документов, меняются независимо). Когда не нужен: когда данные лежат внутри документа.

**Из проекта:** `populate` **не используется**, потому что комментарии и теги вложены в документ диаграммы (вложенный документ и массив), поэтому читаются одним запросом без соединений. Владелец диаграммы это строка `owner` (имя), а не ссылка на коллекцию пользователей.

### Вопрос 11. Как в MongoDB выполнить поиск с условием «поле массива содержит значение» (например, tags содержит «важный»)?

**Ответ.** Для поля-массива простое сравнение значения с полем уже означает «массив содержит это значение»:

```js
Diagram.find({ tags: 'важный' });
```

Расширения: `$in` (содержит хотя бы одно из значений): `{ tags: { $in: ['важный', 'срочно'] } }`; `$all` (содержит все): `{ tags: { $all: ['важный', 'срочно'] } }`; `$size` (длина массива); `$elemMatch` (элемент массива удовлетворяет нескольким условиям сразу). Для массива вложенных документов точечный путь: `{ 'comments.author': 'boris' }`. Ускоряет поиск индекс по полю массива (multikey).

**Из проекта:** `diagrams.controller.js`, строка 13: `{ tags: tag }` для `?tag=shop` и строка 14: `{ 'comments.author': commentAuthor }` для `?commentAuthor=boris`. Снимок 10 (`09-filter-by-tag.png`) показывает работу фильтра. Индексы: `diagram.js`, строки 42 и 51.

## 7. Частые ошибки

1. **Сохранять строку подключения в коде или коммите.** Только `.env` и `.gitignore`; в чат и отчёт не переносить (на снимке показывать значение с затёртым паролем).
2. **Не разрешить IP в Atlas.** Atlas по умолчанию блокирует чужие адреса: нужно добавить текущий IP в Network Access, иначе подключение «висит» до таймаута.
3. **Специальные символы в пароле пользователя.** Их нужно кодировать в строке подключения (`%40` вместо `@`), проще взять пароль из букв и цифр.
4. **Не запустить валидаторы при обновлении.** Без `runValidators: true` `findByIdAndUpdate` пропустит неверные данные.
5. **Забыть `new: true`.** Метод вернёт документ до изменения.
6. **Принимать запрос как есть.** `{"owner": {"$ne": null}}` вернёт всё (NoSQL-инъекция); проверять типы, использовать `sanitizeFilter`.
7. **Передавать `_id` не той длины.** Любая строка вместо 24 hex-символов даст `CastError` (500 вместо понятных 400).
8. **Забыть, что `_id` это не строка.** При сравнении в JS нужно приводить к строке.
9. **Неограниченные массивы.** Комментарии без предела раздувают документ; в нашем коде предел 100 с проверкой в условии `$push`.
10. **Объявить `/:id` раньше `/stats`.** Слово `stats` станет идентификатором.
11. **Забыть индексы для частых фильтров.** Запрос работает, но медленно.
12. **Путать `_id` и `id`.** Наружу отдаётся `id` (виртуальное поле), в базе `_id`.
13. **Полагаться на удалённую базу без таймаута.** Приложение «висит» вместо ответа 503.
14. **На защите:** говорить «связь через `populate`», когда у нас вложенные документы. Объясните выбор: данные читаются вместе, поэтому вложение проще и быстрее.

Проверка перед защитой: `npm install`, `npm test` (тесты поднимают временную MongoDB в памяти и рабочую базу не трогают), `npm start` с рабочим `.env`, затем создать диаграмму с тегами, добавить комментарий, `GET /diagrams?tag=shop`, `?commentAuthor=boris`, `?q=order`, `/diagrams/stats`; остановить MongoDB и повторить запрос (ответ 503).
