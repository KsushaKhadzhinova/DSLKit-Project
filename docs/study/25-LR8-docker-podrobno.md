## 3. Теория Docker

### 3.1. Зачем нужен Docker: «у меня работает»

Приложению нужна среда: версия Node.js, библиотеки, база данных, настройки. У разработчика это одно, на сервере другое, и появляется «у меня работает, а у вас нет». Docker упаковывает приложение **вместе со средой** в образ. Образ запускается одинаково на ноутбуке, у коллеги и на сервере.

Аналогия: контейнер для морской перевозки. Груз (приложение) уложен в стандартную коробку, и порту всё равно, что внутри: кран и судно работают одинаково.

### 3.2. Образ и контейнер

- **Образ** это неизменяемый шаблон: «установочный диск» с файловой системой и командой запуска. Его нельзя изменить, только собрать новый.
- **Контейнер** это запущенный экземпляр образа: процесс с собственным окружением плюс тонкий **слой для записи** сверху. Из одного образа можно запустить много контейнеров.

Аналогия: образ это рецепт и заготовка торта, контейнер это испечённый торт. Рецепт не меняется, а тортов можно испечь сколько угодно, и каждый можно украсить по-своему (слой записи). Съели торт (удалили контейнер) и украшения исчезли, рецепт цел.

### 3.3. Слои и кэш: «слоёный пирог»

Каждая инструкция Dockerfile (`RUN`, `COPY`, `ADD`) создаёт **слой**: набор изменений файловой системы. Образ это стопка слоёв «только для чтения». Слои совместно используются: два образа на одной базе хранят общие слои один раз.

**Кэш сборки.** Docker запоминает результат каждого слоя. При повторной сборке, если инструкция и всё, что до неё, не изменилось, слой берётся из кэша. Если изменился слой, **все слои после него** пересобираются. Поэтому порядок инструкций важен:

```dockerfile
COPY package.json package-lock.json ./   # меняется редко
RUN npm ci                               # дорогой слой, будет из кэша
COPY . .                                 # меняется часто (код)
```

Сначала копируют только описание зависимостей и ставят их, затем весь код: правка кода не заставляет заново скачивать библиотеки. Так сделано у нас (`backend/Dockerfile`, строки 8–9, 16).

### 3.4. Dockerfile: инструкции по порядку

| Инструкция | Что делает | Пример |
| --- | --- | --- |
| `FROM` | Базовый образ, начало этапа. Обязательна, с неё начинается Dockerfile (до неё допустим только `ARG`). | `FROM node:22-alpine AS deps` |
| `ARG` | Переменная, доступная только **при сборке** (`--build-arg`). До первого `FROM` её можно использовать в самом `FROM`. | `ARG REGISTRY=` |
| `ENV` | Переменная окружения, сохраняется в образе и доступна при запуске. | `ENV PORT=3000` |
| `WORKDIR` | Рабочая папка для последующих инструкций (создаётся сама). | `WORKDIR /app` |
| `COPY` | Копирует файлы из контекста (или `--from=` другого этапа) в образ. | `COPY package.json ./` |
| `ADD` | Как `COPY`, плюс распаковка архивов и URL. Обычно используют `COPY`. | |
| `RUN` | Выполняет команду **при сборке** и сохраняет результат слоем. | `RUN npm ci` |
| `USER` | От имени какого пользователя работают дальнейшие команды и сам контейнер. | `USER node` |
| `EXPOSE` | Документирует порт приложения. Порт на хосте **не открывает**. | `EXPOSE 3000` |
| `HEALTHCHECK` | Команда проверки здоровья контейнера. | см. 4.1 |
| `CMD` | Команда **по умолчанию** при запуске контейнера; заменяется аргументами `docker run`. | `CMD ["node", "server.js"]` |
| `ENTRYPOINT` | Неизменяемая точка входа; `CMD` тогда задаёт её аргументы по умолчанию. | `ENTRYPOINT ["node"]` |
| `VOLUME` | Объявляет точку монтирования тома. | `VOLUME /data` |
| `LABEL` | Метаданные образа. | |

**`RUN`, `CMD`, `ENTRYPOINT`** путают чаще всего: `RUN` работает **один раз при сборке**, `CMD` и `ENTRYPOINT` **при каждом запуске контейнера**. Форма в квадратных скобках (`["node", "server.js"]`, exec-форма) запускает процесс напрямую, он получает сигналы остановки; форма строкой запускает через оболочку `sh -c`.

**CMD и ENTRYPOINT.** `ENTRYPOINT ["node"]` и `CMD ["server.js"]` дают запуск `node server.js`; `docker run image other.js` заменит только `CMD`, будет `node other.js`. `ENTRYPOINT` заменяется только флагом `--entrypoint`.

### 3.5. Многоэтапная сборка (multi-stage)

Чтобы собрать React, нужны Node.js и сотни мегабайт `node_modules`. Чтобы отдавать готовые файлы, нужен только веб-сервер. Многоэтапная сборка делает два образа в одном файле:

```dockerfile
FROM node:22-alpine AS builder      # этап 1: сборка
RUN npm run build                   # получили папку dist
FROM nginx:alpine                   # этап 2: итоговый образ
COPY --from=builder /app/dist /usr/share/nginx/html   # берём только dist
```

В итоговый образ попадает только последний `FROM` и то, что явно скопировано через `COPY --from=`. Node.js, исходники и `node_modules` остаются в промежуточном этапе и в итоговый образ не входят. Аналогия: на кухне готовят блюдо (этап сборки), а гостю на стол несут только готовое блюдо, без грязной посуды и сырых продуктов.

Это ответ на вопрос 2 задания: `COPY --from=builder` берёт файлы из этапа с именем `builder`.

### 3.6. `.dockerignore`

Файл со списком шаблонов, которые не попадают в **контекст сборки** (то, что `docker build` отправляет демону). Зачем: сборка быстрее (не передаём `node_modules`, тесты, `.git`), образ меньше и чище, и **в образ не попадают секреты** (`.env`). У нас это `Dockerfile.dockerignore` рядом с Dockerfile (так BuildKit находит файл, когда контекст сборки в другой папке).

### 3.7. Тома и сети

**Тома (volumes).** Файловая система контейнера живёт, пока жив контейнер. Удалили или пересоздали контейнер, и данные внутри пропали. Для базы данных это недопустимо. **Том** это хранилище вне контейнера, которым управляет Docker; он подключается в нужную папку (`pgdata:/var/lib/postgresql/data`). Контейнер можно удалить и пересоздать, а данные остаются. `docker compose down` том сохраняет, `docker compose down -v` удаляет.

Аналогия: контейнер это съёмная квартира, том это склад, куда вы сдали вещи: из квартиры съехали, вещи на складе.

Виды: именованный том (`pgdata`), bind mount (папка хоста), `tmpfs` (память).

**Сети.** Compose создаёт для стека сеть, и контейнеры находят друг друга **по имени сервиса**: Docker ведёт встроенный DNS. Поэтому в строке подключения хост `db`, а в Nginx `http://backend:3000`. Можно создавать несколько сетей и состыковывать сервисы выборочно (изоляция). Сеть с `internal: true` не имеет выхода наружу.

### 3.8. Docker Compose

Файл `docker-compose.yml` (или `compose.yaml`) описывает стек. Основные ключи сервиса:

| Ключ | Смысл |
| --- | --- |
| `image` | Готовый образ (из реестра). |
| `build` | Собрать образ: `context` (папка), `dockerfile`, `args`. |
| `ports` | Публикация портов `"хост:контейнер"`. |
| `environment` | Переменные окружения контейнера (или `env_file`). |
| `volumes` | Тома и bind mount. |
| `depends_on` | Порядок запуска; с `condition: service_healthy` ждёт здоровья. |
| `healthcheck` | Как проверять здоровье: `test`, `interval`, `timeout`, `retries`, `start_period`. |
| `networks` | К каким сетям подключён. |
| `restart` | Политика перезапуска (`no`, `on-failure`, `always`, `unless-stopped`). |
| `command` | Переопределение `CMD`. |
| `profiles` | Сервис запускается только при указании профиля. |

**`depends_on` и готовность.** Просто `depends_on: [db]` ждёт только **запуска** контейнера, а не готовности базы (PostgreSQL запускается ещё несколько секунд, и сервер упадёт, не достучавшись). Решение: `healthcheck` у базы и `condition: service_healthy`.

**`healthcheck`.** Docker периодически выполняет команду. Код 0 значит «здоров»; после нескольких неудач (`retries`) статус `unhealthy`. Параметры: `interval` как часто проверять, `timeout` сколько ждать ответа, `retries` сколько неудач подряд считается сбоем, `start_period` льготное время при старте.

**Переменные из `.env`.** Compose сам читает файл `.env` рядом с `docker-compose.yml` и подставляет значения в `${ИМЯ}`: `${POSTGRES_USER:-dslkit}` (значение по умолчанию), `${POSTGRES_PASSWORD:?сообщение}` (ошибка, если не задано). Через `environment:` значение попадает уже внутрь контейнера.

**Основные команды Compose:**

| Команда | Действие |
| --- | --- |
| `docker compose up --build` | Собрать образы и запустить стек. |
| `docker compose up -d` | Запустить в фоне. |
| `docker compose down` | Остановить и удалить контейнеры и сети (тома остаются). |
| `docker compose down -v` | То же и удалить тома (данные БД стираются). |
| `docker compose ps` / `docker ps` | Список контейнеров. |
| `docker compose logs -f backend` | Логи сервиса (`-f` следить). |
| `docker compose exec backend sh` | Оболочка внутри запущенного контейнера. |
| `docker compose up --scale backend=3` | Несколько экземпляров сервиса. |
| `docker compose --profile tools up -d pgadmin` | Запустить сервис профиля. |

### 3.9. Docker Hub, теги и публикация

Образ называется `[реестр/][пользователь/]репозиторий:тег`. Без реестра подразумевается Docker Hub, без тега `latest` (последняя, но «плавающая» версия: лучше указывать явно, как `postgres:16-alpine`).

Типовой путь публикации:

```bash
docker login                               # вход в реестр (пароль или токен вводит владелица)
docker build -t dslkit-backend .           # сборка
docker tag dslkit-backend <пользователь>/dslkit-backend:1.0   # второе имя
docker push <пользователь>/dslkit-backend:1.0                 # загрузка
docker pull <пользователь>/dslkit-backend:1.0                 # скачивание на другой машине
```

Для другого реестра в имя добавляют его адрес: `registry.gitlab.com/<группа>/<проект>/backend:1.0`, `ghcr.io/<пользователь>/dslkit-backend:1.0`. Вход: `docker login registry.gitlab.com`.

**Доступ к образам в Беларуси.** Docker Hub может быть недоступен. Три выхода, все описаны в задании:

1. **Зеркало для всего демона** в `daemon.json`: `"registry-mirrors": ["https://mirror.gcr.io", "https://dockerhub.timeweb.cloud"]`.
2. **Префикс зеркала в имени образа:** у нас переменная `REGISTRY=mirror.gcr.io/` (с косой чертой на конце) подставляется перед именами образов в обоих Dockerfile и в Compose.
3. **Другой реестр:** образы из `registry.gitlab.com`, `quay.io` и т.п., свои образы публиковать в GitLab Container Registry.

### 3.10. Образ и виртуальная машина

| | Виртуальная машина | Контейнер |
| --- | --- | --- |
| Что изолирует | целая ОС с собственным ядром | процесс на общем ядре хоста |
| Размер | гигабайты | мегабайты (десятки-сотни) |
| Запуск | минуты | секунды |
| Накладные расходы | высокие (гипервизор, своя ОС) | низкие |
| Изоляция | сильнее (отдельное ядро) | слабее (общее ядро), поэтому важны ограничения |
| Единица распространения | образ диска | образ Docker из слоёв |

Аналогия: виртуальная машина это отдельный дом со своим фундаментом и коммуникациями, контейнер это квартира в общем доме: стены свои, а фундамент и трубы общие.

На Windows и macOS Docker Desktop запускает контейнеры Linux внутри лёгкой виртуальной машины (WSL 2).

### 3.11. Безопасность: на что смотреть

1. **Не запускать от root.** `USER node` в Dockerfile, образ `nginx-unprivileged` слушает порт 8080 без прав суперпользователя.
2. **Секреты не в образ.** Пароли и ключи не пишутся в Dockerfile (`ENV PASSWORD=...`) и не копируются файлом `.env` в образ (`.env` в `.dockerignore`): всё, что попало в слой, можно извлечь из образа. Секреты передаются при запуске через переменные окружения из `.env`, который лежит вне репозитория (`.gitignore`). В Compose обязательные значения помечены `:?`, чтобы запуск без них не стартовал.
3. **Минимальная база.** Alpine и многоэтапная сборка: меньше пакетов, меньше уязвимостей.
4. **Закреплённые версии.** `postgres:16-alpine`, а не `latest`.
5. **Отобрать лишнее.** `cap_drop: [ALL]`, `no-new-privileges`, `read_only: true` (корневая файловая система только для чтения), `tmpfs` для временных файлов.
6. **Не публиковать лишние порты.** Порт базы на хост не открыт; порт backend привязан к `127.0.0.1`.
7. **Изолировать сети.** База в сети `internal: true`.
8. **Ограничить ресурсы.** `mem_limit`, `pids_limit`, ротация логов.
9. **Проверять здоровье и перезапускать.** `healthcheck`, `restart: unless-stopped`.

```dockerfile

- Строка 18: `USER node`: сервер работает **не от root** (в официальном образе пользователь `node` уже есть).
- Строка 19: `EXPOSE 3000` документирует порт.

```dockerfile
20 HEALTHCHECK --interval=15s --timeout=3s --start-period=20s --retries=3 \
21   CMD node -e "fetch('http://127.0.0.1:'+process.env.PORT+'/health').then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"

Три шага: миграции создают таблицы, сид создаёт администратора (пропускается без `ADMIN_EMAIL`), затем **`exec node server.js`**: `exec` заменяет оболочку процессом Node, он становится главным (PID 1) и получает сигнал остановки от Docker.

### 4.3. `frontend/Dockerfile` (клиент, многоэтапная сборка)

```dockerfile
2  ARG REGISTRY=
5  FROM ${REGISTRY}library/node:22-alpine AS builder
6  WORKDIR /app
7  COPY package.json package-lock.json ./
8  RUN npm ci
9  COPY . .

```

- Строка 5: этап `builder` (именно так называется в примере задания и в вопросе 2).
- Строка 8: `npm ci` без `--omit=dev`: для сборки Vite нужны и dev-зависимости.
- Строки 11–12: **адрес API в клиенте задан как `/api`** на этапе сборки. Vite вшивает `VITE_*` в сборку, поэтому значение нужно задать до `npm run build`. Браузер обращается на тот же адрес, откуда загрузил страницу, а Nginx пересылает `/api/` на backend. Адрес сервера не вшит, CORS не нужен.
- Строка 13: `npm run build` создаёт папку `dist` со статическими файлами.

```dockerfile
16 FROM ${REGISTRY}nginxinc/nginx-unprivileged:1.27-alpine
17 COPY --from=deploy nginx.conf /etc/nginx/conf.d/default.conf
18 COPY --from=builder /app/dist /usr/share/nginx/html
20 EXPOSE 8080
21 HEALTHCHECK --interval=15s --timeout=3s --start-period=5s --retries=3 \
22   CMD wget -q -O /dev/null http://127.0.0.1:8080/ || exit 1

```

- Строка 16: итоговый образ: Nginx, который работает **не от root** и слушает порт 8080 (непривилегированный порт). В итоговом образе нет Node.js и исходников.
- Строка 17: `--from=deploy` берёт `nginx.conf` из **именованного дополнительного контекста** `deploy` (в Compose `additional_contexts: deploy: ./frontend`); нужен потому, что основной контекст сборки это папка клиента ЛР5, а конфиг лежит в папке ЛР8.
- Строка 18: **`COPY --from=builder`**: из этапа сборки забирается только `dist` и кладётся в папку, откуда Nginx отдаёт страницы.

- Строки 21–22: healthcheck: `wget` (есть в Alpine) запрашивает главную страницу.

### 4.4. `frontend/nginx.conf` (веб-сервер и обратный прокси)

```nginx
1  limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
4  listen 8080;   6  server_tokens off;   8  client_max_body_size 100k;
9  root /usr/share/nginx/html;   10 index index.html;
12 add_header X-Content-Type-Options "nosniff" always;  ... Content-Security-Policy ...
18 location /api/ {
19   proxy_pass http://backend:3000/;
20   limit_req zone=api burst=20 nodelay;
21   proxy_set_header Host $host;
22   proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
23   proxy_set_header X-Forwarded-Proto $scheme;
24   proxy_read_timeout 15s;
29 location /assets/ { expires 1y; add_header Cache-Control "public, immutable"; ... }
39 location / { try_files $uri /index.html; }
```

- Строка 1: зона ограничения частоты: 10 запросов в секунду с одного адреса (память 10 МБ).
- Строки 6, 8: `server_tokens off` скрывает версию Nginx; тело запроса не больше 100 КБ.
- Строки 12–15: заголовки безопасности (`nosniff`, запрет вставки в рамку, `Referrer-Policy`, строгая CSP).
- Строки 18–25: **Reverse proxy** (дополнительное требование). `proxy_pass http://backend:3000/` обращается к сервису по **имени `backend`** (DNS сети Compose, вопрос 3 задания). Завершающая `/` отрезает префикс `/api`, так что `/api/health` превращается в `/health`. `limit_req` с `burst=20` пропускает короткие всплески. `X-Forwarded-For` передаёт адрес клиента (сервер при `TRUST_PROXY=1` его читает).
- Строки 29–36: файлы `assets/` с хешем в имени кэшируются на год. Комментарий в строке 28: `location` со своим `add_header` не наследует заголовки сервера, поэтому они повторены.
- Строки 39–41: `try_files $uri /index.html`: для одностраничного приложения неизвестные адреса отдают главную страницу (маршрутизацию делает React).

## 6. Вопросы преподавателя (вариант 26: вопросы 9, 10, 11)

### Вопрос 9. Как в Docker Compose задать зависимость запуска контейнеров (чтобы база данных стартовала раньше backend)?

**Ответ.** Ключом `depends_on` в описании сервиса `backend`:

```yaml
backend:
  depends_on:
    db:
      condition: service_healthy
db:
  healthcheck:
    test: ['CMD-SHELL', 'pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}']
    interval: 5s
    timeout: 3s
    retries: 10
```

Важное различие. Простая запись `depends_on: [db]` гарантирует только порядок **запуска контейнеров**: `db` стартует раньше, но PostgreSQL внутри контейнера может ещё несколько секунд инициализироваться, и сервер, не достучавшись до базы, упадёт. Условие `service_healthy` заставляет Compose ждать, пока у `db` healthcheck (`pg_isready`) станет «здоров». Другие условия: `service_started` (по умолчанию) и `service_completed_successfully` (дождаться завершения разовой задачи, например миграции). Дополнительно приложению полезно уметь повторять подключение к базе.

**Из проекта:** `docker-compose.yml`, строки 47–49 (`backend` ждёт `db` по `service_healthy`), строки 25–29 (healthcheck базы), строки 71–73 (`frontend` ждёт здоровый `backend`). Цепочка запуска: `db` → `backend` → `frontend`.

### Вопрос 10. Как выполнить команду внутри запущенного контейнера (например, зайти в оболочку)?

**Ответ.** Командой `docker exec`. Флаги `-i` (интерактивно) и `-t` (псевдотерминал) вместе дают оболочку:

```bash
docker exec -it <имя-или-id-контейнера> sh        # оболочка (в Alpine вместо bash есть sh)
docker exec <контейнер> ls /app                   # разовая команда без оболочки
docker compose exec backend sh                    # то же через Compose, по имени сервиса
docker compose exec db psql -U <пользователь> -d <база>   # консоль PostgreSQL
```

`docker exec` запускает **новый процесс** в уже работающем контейнере. Не путать с `docker run`, который создаёт и запускает **новый** контейнер из образа, и с `docker attach`, который подключается к главному процессу. Узнать имя контейнера: `docker ps`. Для Alpine-образов оболочка `sh`, а не `bash`. Выход: `exit`.

**Из проекта:** `docker compose exec backend sh` открывает оболочку сервера (запущенной под пользователем `node`), `docker compose exec db psql ...` консоль базы для проверки таблиц после миграций. Имена контейнеров формируются от проекта: `dslkit-backend-1` и так далее (`docker ps`).

### Вопрос 11. Как пробросить порт с хоста в контейнер в Docker Compose?

**Ответ.** Ключом `ports` в формате `"порт_хоста:порт_контейнера"`:

```yaml
ports:
  - '8080:8080'                 # хост 8080 -> контейнер 8080 (доступно отовсюду)
  - '127.0.0.1:3000:3000'       # только с этого компьютера
  - '80:8080'                   # внешний 80 на внутренний 8080
```

Порт хоста слева, порт контейнера справа. Без привязки к адресу порт открывается на всех сетевых интерфейсах; `127.0.0.1:` оставляет его только локальным. Инструкция `EXPOSE` в Dockerfile порт **не публикует**, она только документирует. Если порт нужен лишь другим контейнерам стека, публиковать его не нужно: внутри сети контейнеры обращаются друг к другу по имени сервиса и порту контейнера (так база у нас не опубликована).

**Из проекта:** `docker-compose.yml`, строка 74: `'${FRONTEND_PORT:-8080}:8080'` (клиент), строка 52: `'127.0.0.1:${BACKEND_PORT:-3000}:3000'` (сервер только для проверок с хоста), строка 99: pgAdmin на `127.0.0.1`. У базы `ports` нет совсем. Порты задания 80 и 5000 получаются настройкой `FRONTEND_PORT=80` и `BACKEND_PORT=5000` в `.env`.

## 7. Частые ошибки

1. **Падение backend с `password authentication failed`.** Это находка повторного запуска 28 октября: PostgreSQL берёт пароль **только при первой инициализации тома**. Если том `dslkit_pgdata` остался от прежнего запуска с другим паролем, новый `POSTGRES_PASSWORD` из `.env` к нему не подходит. Лечение: `docker compose down -v` (сотрёт данные базы) или вернуть прежний пароль.
2. **Забыть `.env`.** Compose остановится с сообщением «set POSTGRES_PASSWORD in .env»: так и задумано.
3. **Docker не запущен.** `Cannot connect to the Docker daemon`: запустить Docker Desktop.
4. **Порт занят.** Порт 80 часто занят (IIS, Skype). Использовать 8080 или освободить порт.
5. **`depends_on` без `service_healthy`.** Backend стартует раньше готовности базы и падает.
6. **Хост базы `localhost` внутри контейнера.** Внутри контейнера `localhost` это он сам; база доступна по имени сервиса `db`.
7. **Секреты в образе или репозитории.** Не писать пароли в Dockerfile и Compose, не копировать `.env` в образ (`.dockerignore`), не коммитить `.env`.
8. **`latest` вместо версии.** Образ может измениться сам; указывать тег (`postgres:16-alpine`).
9. **Копировать весь проект до установки зависимостей.** `COPY . .` перед `npm ci` ломает кэш: каждая правка кода заново ставит библиотеки.
10. **Не запускать `npm ci --omit=dev` в итоговом образе.** Образ раздувается dev-зависимостями.
11. **CMD строкой вместо списка.** Процесс запускается через `sh -c` и не получает сигнал остановки: контейнер останавливается медленно. В нашей `CMD` для этого стоит `exec`.
12. **`EXPOSE` считать открытием порта.** Порт открывает только `ports`.
13. **Переменные `VITE_*` не в сборке.** Vite вшивает их при `npm run build`; задавать надо через `ARG` на этапе сборки, а не при запуске контейнера.
14. **Контейнер не живёт.** Главный процесс завершился (например, `nginx` без `daemon off;`): контейнер выходит вместе с ним.
15. **Ждать доступа к Docker Hub в РБ.** Заранее настроить зеркало (`registry-mirrors`) или `REGISTRY=mirror.gcr.io/`, указать в отчёте, что использовано.
16. **Забыть, что `down -v` стирает данные.** Использовать осознанно.
17. **Путать образ и контейнер** (вопрос 1): образ шаблон, контейнер экземпляр.
18. **Сообщать, что образ опубликован в Docker Hub.** Публикация не делалась (нужен вход владелицы).

Проверка перед защитой: создать `.env` из `.env.example` (значения вписать самой), `docker compose up --build`, `docker ps` (три контейнера `healthy`), открыть `http://localhost:8080`, зарегистрироваться, создать диаграмму, проверить `http://localhost:8080/api/health`; `docker compose down` и снова `up` (данные на месте благодаря тому); `docker compose down -v` (данных нет). Статические проверки файлов без Docker: `npm test` в папке `part-2/lab-08-docker`.
