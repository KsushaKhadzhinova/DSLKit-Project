# ПЗ2: как работают PATCH и DELETE (шпаргалка и разбор)

Английская версия: `36-PZ2-PATCH-DELETE.en.md`. Код: `part-2/pz-02-rest-api/src/resource.js` (`createResourceRouter`), проверки в `src/validation.js`, связи в `src/app.js`. Листинги для приложения отчёта (передать T38): обработчики `router.patch` и `router.delete`, функции `requireFresh` и `etagOf`.

## PATCH `/api/{ресурс}/:id`

Порядок шагов обработчика:

1. `load(req)`: `parseId` (не положительное целое: 400 `invalid_id`), поиск записи (нет: 404 `not_found`).
2. `requireFresh`: если пришёл `If-Match` и тег не совпал с текущим состоянием записи, 412 `precondition_failed`; без заголовка шаг пропускается.
3. `body(req, true, item)`: обрезка пробелов (`trimStrings`), `validate` в режиме `partial` (обязательные поля не требуются, присланные проверяются, пустой объект и неизвестные поля дают 400), затем `hooks.check`: уникальность почты (409 `conflict`) или существование родителя (409 `parent_missing`).
4. `collection.update(item, data)` меняет только присланные поля, `id` и `createdAt` остаются.
5. Ответ 200 с записью и новым `ETag`.

Всё до шага 4 только проверяет, поэтому при любой ошибке запись **не изменена** (откат не нужен). Обработчик синхронный: между проверкой и записью другой запрос вклиниться не может.

## PUT отличается

`validate` без `partial`: обязательные поля нужны; пропущенное необязательное поле сохраняет текущее значение (`applyDefaults` с `current`), а не сбрасывается.

## DELETE `/api/{ресурс}/:id`

1. `load` (400 или 404), 2. `requireFresh` (412), 3. `hooks.beforeRemove`: у пользователя есть проекты или у проекта есть диаграммы, 409 `conflict` (**каскада нет**, запрет), 4. `collection.remove`, ответ 204 без тела.

Повторный DELETE: первый 204, второй 404. Состояние сервера после обоих одинаково (записи нет), поэтому метод идемпотентен по результату; код ответа другой, это нормально.

## Гонки и «невозможные» сценарии (тесты `test/consistency.test.js`)

| Сценарий | Результат |
| --- | --- |
| Создание проекта или диаграммы для удалённого родителя | 409 `parent_missing`, ничего не сохранено |
| PATCH, PUT, DELETE, publish, duplicate удалённой записи | 404 в едином формате |
| PATCH и DELETE одной записи одновременно | DELETE 204, PATCH 200 или 404, запись удалена |
| Два DELETE одновременно | 204 и 404 |
| Создание дочерней записи и удаление родителя одновременно | выигрывает ровно одно, висячих записей нет |
| Два писателя с одним `ETag` | 200 и 412 |
| Удаление родителя с детьми | 409, каскада нет |

Почему гонки безопасны: Node выполняет JavaScript в одном потоке, а обработчики не содержат `await` между проверкой и изменением. В версии с настоящей БД это место потребовало бы транзакции (`SELECT ... FOR UPDATE` или ограничение внешнего ключа).

## Вероятные вопросы

- Чем PATCH отличается от PUT? См. выше; PATCH не требует всех полей, PUT заменяет запись целиком.
- Что вернёт PATCH с пустым телом? 400 `validation_failed` «send at least one field to change».
- Зачем `If-Match`? Чтобы форма, открытая давно, не затёрла чужое изменение; без него запись безусловная.
- Почему 404, а не 204, при повторном DELETE? Записи нет, это честный ответ; идемпотентность про состояние, не про код.
- Допиши при мне: `PATCH` с проверкой «нельзя менять `role` на `owner`» (в `hooks.check` у users бросить `ApiError(403, ...)`), или `DELETE` с мягким удалением (поле `deletedAt` вместо `collection.remove`).
