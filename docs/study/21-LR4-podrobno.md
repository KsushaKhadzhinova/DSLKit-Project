## 3. Теория подробно

### 3.1. Состояние: «табло» компонента

Представьте табло на вокзале. Оно показывает данные, и когда данные меняются, табло перерисовывается. Состояние (`useState`) это те самые данные на табло. Если вы измените переменную обычным присваиванием (`let x = 1; x = 2`), React об этом не узнает и экран не изменится. Только вызов установщика (`setX`) сообщает: «данные поменялись, нарисуй заново».

`useState` возвращает пару `[значение, установщик]`. Нельзя менять значение напрямую (`diagrams.push(...)`): React сравнивает **ссылки**, а у изменённого на месте массива ссылка прежняя, поэтому перерисовки не будет. Нужно создавать новый массив: `[...prev, новый]`, `prev.filter(...)`, `prev.map(...)`. Это и есть иммутабельность.

### 3.2. Функциональное обновление: «очередь у кассы»

`setDiagrams([...diagrams, x])` использует значение `diagrams` **на момент отрисовки**. Если два клика произошли до следующей отрисовки, оба возьмут одно и то же старое значение, и первое изменение потеряется. `setDiagrams(prev => [...prev, x])` отдаёт React функцию: он применяет их по очереди, каждая получает результат предыдущей. Это как очередь у кассы: каждый следующий видит остаток после предыдущего, а не снимок, сделанный в начале дня.

Отсюда же ответ на вопрос 10: после `setState` переменная в **этом же вызове** остаётся старой, потому что обновление только запланировано.

### 3.3. Эффекты: «поручения после уборки»

Функция компонента должна быть «чистой»: по props и состоянию вернуть картинку. Всё остальное (писать в хранилище, ставить таймер, менять заголовок вкладки) это поручения, которые выполняются **после** того, как картинка нарисована. Это `useEffect`.

Массив зависимостей это условие «когда выполнять поручение»:

- `useEffect(f)` без массива: после каждой отрисовки (почти всегда лишнее);
- `useEffect(f, [])`: один раз после первого появления;
- `useEffect(f, [a, b])`: после первого появления и каждый раз, когда изменилось `a` или `b`.

Функция очистки это «убрать за собой»: её вызывают перед следующим запуском эффекта и при удалении компонента. Классический пример: таймер. Без очистки старые таймеры накапливаются и срабатывают вразнобой.

### 3.4. Debounce на таймере: «лифт ждёт, пока все зайдут»

Лифт не закрывает двери сразу после первого пассажира: он ждёт паузу. Если пришёл ещё один, отсчёт начинается заново. Так и debounce: каждое изменение ставит таймер на 500 мс, а следующее изменение сначала отменяет прежний таймер (`clearTimeout` в очистке эффекта), затем ставит новый. Действие выполняется только когда за 500 мс ничего не менялось. У нас так работает индикатор «Сохранение…» → «Сохранено».

### 3.5. `localStorage`: «блокнот в кармане»

Хранилище браузера принимает только строки и привязано к сайту. Поэтому объект превращают в строку (`JSON.stringify`), а при чтении обратно (`JSON.parse`). Читать нужно осторожно: пользователь мог вручную испортить значение, другая версия приложения могла записать другой формат. Поэтому чтение обёрнуто в `try/catch`, а данные проверяют функцией формы (`isDiagramList`).

`localStorage` живёт, пока его не очистят; `sessionStorage` до закрытия вкладки. Оба синхронные (блокируют поток), поэтому большие данные в них не кладут.

### 3.6. Ленивая инициализация: «не вскрывать сейф на каждый вопрос»

`useState(readStorage())` вызвал бы `readStorage` при **каждой** отрисовке (результат отбрасывался бы, но чтение выполнялось бы). `useState(() => readStorage())` передаёт функцию, и React вызывает её один раз, при первом рендере.

### 3.7. Производные данные не хранят

Отфильтрованный и отсортированный список можно вычислить из `diagrams`, `query`, `status`, `sortBy`. Если положить его ещё и в состояние, придётся следить, чтобы обе копии не разошлись. Поэтому `visible` считается при отрисовке (в `useMemo`, чтобы не пересчитывать, пока ничего не изменилось).

### 3.8. Контролируемые поля

Контролируемое поле: `<input value={title} onChange={e => setTitle(e.target.value)} />`. Состояние хранит текст, поле его только показывает. Плюс: можно проверять и менять ввод на лету. Неконтролируемое поле хранит значение само в DOM (читается через `ref`). Для форм с проверкой выбирают контролируемые.

### 3.9. Горячие клавиши и формы

Если поле лежит внутри `<form onSubmit=...>`, клавиша Enter отправляет форму сама, отдельный обработчик не нужен. Для поля вне формы (у нас редактирование названия в карточке) вешают `onKeyDown` и сравнивают `event.key` с `'Enter'` или `'Escape'`.

### 3.10. Оптимизация большого списка

Три уровня: `React.memo` (не перерисовывать карточку, чьи props не менялись), `useMemo`/`useCallback` (стабильные значения и функции, чтобы `memo` срабатывал), виртуализация (рисовать только видимые строки, библиотеки вроде `react-window`). У нас список ограничен 200 записями, поэтому достаточно `memo`, `useMemo`, `useCallback`.

### 4.3. `src/hooks/useLocalStorage.js` (хук хранения)

```js
3  function readStorage(key, fallback, validate, repair) {
4    try {
5      const raw = localStorage.getItem(key);
6      if (raw === null) return fallback;
7      const parsed = JSON.parse(raw);
8      if (validate(parsed)) return parsed;
10     return repair?.(parsed) ?? fallback;
11   } catch {
12     return fallback;
13   }
14 }
```

- Строка 5: читаем строку. Если ключа нет (первый запуск), берём начальные данные (пункт задания «обработайте отсутствие данных»).
- Строка 7: `JSON.parse` превращает строку обратно в массив. Если строка сломана, бросится исключение, и `catch` (строка 11) вернёт начальные данные: приложение не падает.
- Строка 8: `validate` проверяет форму. Строка 10: если форма неверная, `repair` пробует оставить годные записи; `?? fallback` берёт начальные данные, когда спасать нечего.

```js
18 export function useLocalStorage(key, initialValue, validate = () => true, repair) {
19   const [value, setValue] = useState(() => readStorage(key, initialValue, validate, repair));
21   useEffect(() => {
22     try {
23       localStorage.setItem(key, JSON.stringify(value));
24     } catch {
25       // Storage is full or blocked: keep working in memory.
26     }
27   }, [key, value]);
29   return [value, setValue];
30 }
```

- Строка 19: ленивая инициализация (3.6): стрелка `() => readStorage(...)` выполняется один раз.
- Строки 21–27: **задание, часть 3: `useEffect` с зависимостью по данным сохраняет через `JSON.stringify`**. Зависимости `[key, value]`: запись при каждом изменении списка. Ошибка записи (диск полон, хранилище запрещено) гасится: приложение работает в памяти.
- Строка 29: хук возвращает ту же пару, что и `useState`, поэтому в `App` его можно использовать как обычное состояние.
- Загрузка «при монтировании» реализована ленивой инициализацией, а не отдельным `useEffect(..., [])`: это допустимый и более правильный вариант (нет мигания пустого списка). Если преподаватель настаивает на `useEffect([])`, объясните это.

## 6. Вопросы преподавателя (вариант 26: вопросы 9, 10, 11)

В условии 16 вопросов; для варианта 26 номера выбираются как n-1, n, n+1 при n = 10, то есть 9, 10, 11. Ниже развёрнутые ответы на них, а затем краткие ответы на остальные.

### Вопрос 9. Как сохранить объект или массив в localStorage? Как восстановить его обратно?

**Ответ.** `localStorage` хранит только строки. Если записать массив напрямую (`localStorage.setItem('k', arr)`), он превратится в строку вида `"[object Object],[object Object]"`, и данные потеряются. Поэтому:

- **Сохранение:** `localStorage.setItem(key, JSON.stringify(value))`. `JSON.stringify` превращает массив и объекты в текст JSON.
- **Восстановление:** `JSON.parse(localStorage.getItem(key))` превращает текст обратно в массив и объекты.

Особенности, которые стоит назвать:

1. `getItem` возвращает `null`, если ключа нет. `JSON.parse(null)` вернёт `null` (а не ошибку), но нужно явно обработать «нет данных» и взять начальные данные.
2. `JSON.parse` бросает исключение на сломанной строке, поэтому чтение оборачивают в `try/catch`.
3. Даты не восстанавливаются как `Date`: в JSON они строки. У нас даты хранятся строками `ГГГГ-ММ-ДД...` и разбираются через `Date.parse`.
4. Нельзя доверять формату: после чтения данные проверяют (у нас `isDiagramList`).

**Из проекта:** `useLocalStorage.js`, строка 7 (`JSON.parse`), строка 23 (`JSON.stringify`), обёртка `try/catch` в строках 4 и 11, проверка формы в строке 8.

### Вопрос 10. Что произойдёт, если изменить состояние сразу после вызова setState? Будет ли компонент перерендерен мгновенно?

**Ответ.** Нет, не мгновенно. `setState` не меняет переменную в текущем вызове, а **планирует** обновление. React собирает несколько обновлений в пачку (batching) и применяет их одним проходом перед следующей отрисовкой. Поэтому:

```js
setCount(count + 1);
setCount(count + 1); // оба используют одно и то же старое count: итог +1, а не +2
```

Переменная `count` внутри этого обработчика остаётся прежней, перерисовка произойдёт после завершения обработчика. Если новое значение зависит от предыдущего, нужна **функциональная форма**: `setCount(c => c + 1)` дважды даст +2, потому что каждая функция получает результат предыдущей.

**Из проекта:** все изменения списка в `App.jsx` (строки 65, 71, 72, 73) написаны как `setDiagrams(prev => ...)`, поэтому два быстрых клика («Удалить» подряд) не теряют изменения. Значение, нужное сразу после обновления, считают из того же выражения, а не читают из состояния.

### Вопрос 11. Как имитировать асинхронную загрузку данных с сервера с помощью setTimeout в useEffect?

**Ответ.** Заводят состояние `loading` (сначала `true`), в `useEffect` запускают `setTimeout` на нужное время, в нём кладут данные и переключают `loading` в `false`, а в функции очистки отменяют таймер (`clearTimeout`), чтобы не писать в уже удалённый компонент:

```js
const [loading, setLoading] = useState(true);
useEffect(() => {
  const timer = setTimeout(() => setLoading(false), 1000);
  return () => clearTimeout(timer);
}, []);
// в JSX: {loading ? <p>Загрузка…</p> : <List ... />}
```

Пока `loading` истинно, показывается индикатор, затем список.

**Из проекта:** `useServerLoad.js` (строки 7–17), использование в `App.jsx` (строка 57 и условный вывод в строках 107–111): секундная «Загрузка диаграмм…» перед списком. Массив зависимостей у нас `[loading]` и ранний выход `if (!loading) return`: эффект ничего не делает, когда загрузка уже закончена.

## 7. Частые ошибки

1. **Менять состояние напрямую.** `diagrams.push(x); setDiagrams(diagrams)`: ссылка прежняя, экран не обновится. Нужен новый массив.
2. **Обновлять по устаревшему значению.** `setDiagrams([...diagrams, x])` в обработчиках, которые срабатывают подряд. Использовать `prev =>`.
3. **Забыть массив зависимостей.** Эффект без второго аргумента выполняется после каждой отрисовки; если внутри `setState`, получится бесконечный цикл.
4. **Не очищать таймеры.** Без `clearTimeout` старые таймеры срабатывают позже и «мигают» статусом; в StrictMode ошибку видно сразу (двойной запуск).
5. **Читать `localStorage` на каждом рендере.** Писать `useState(readStorage())` вместо `useState(() => readStorage())`.
6. **Доверять содержимому хранилища.** Без `try/catch` и проверки формы сломанный JSON роняет приложение (проверка: `localStorage.setItem('dslkit.diagrams', '{broken')` и обновить страницу, приложение должно вернуться к начальному списку).
7. **Хранить производные данные в состоянии.** Отфильтрованный список в отдельном `useState` придётся синхронизировать вручную.
8. **Забыть `key` или брать индекс.** При удалении и сортировке индекс как ключ даёт «прыгающие» значения в полях карточек.
9. **Не вызвать `preventDefault` в форме.** Страница перезагрузится, данные формы потеряются.
10. **Вызвать хук в условии или цикле.** Нарушает порядок хуков.
11. **Записать число или объект как значение ключа без `stringify`.** Получится `[object Object]`.
12. **Показать ошибку только цветом.** Нужен текст с `role="alert"`, а не только красная рамка.
13. **На защите:** назвать загрузку из `localStorage` «через `useEffect`», когда в коде ленивая инициализация. Объясните, что это тот же смысл «загрузить при старте» и более правильная реализация.
