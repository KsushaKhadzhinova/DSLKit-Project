# Архитектурное ревью DSLKit

Английская версия (краткая): [`ARCHITECTURE-REVIEW.en.md`](ARCHITECTURE-REVIEW.en.md). Дата среза: 29 октября 2026. Код не менялся, ничего не коммитилось. Значения секретов не читались и не приводятся: проверялись только имена переменных, наличие файлов и правила `.gitignore`.

Обозначения: S до часа, M до полудня, L больше дня. «Защита» оценивает влияние на защиту лабораторных и курсового.

## 1 Верна ли архитектура

### 1.1 Часть 1 (сайт)

Что сделано хорошо:

- Клиент без сборки, ES-модули, слои `api / components / engines / notations / storage / utils`: для цели Части 1 (HTML, CSS, JS, DOM, 100% покрытие тестами без бандлера) это верный выбор, тесты идут на `node --test` и jsdom.
- Строгая CSP (`tools/server.js`), очистка чужого SVG, `textContent`, service worker не кэширует чужие адреса.
- Свой API отрисовки `tools/render-api.js` (209 строк) с запасным вариантом через Kroki: общий сервис не единственная точка отказа.
- Зависимости корня минимальны: одна runtime-зависимость (`lodash`).

Ограничения, которые нужно честно назвать на защите:

- «Аккаунты в браузере» (`site/js/storage/accounts.js`) это не аутентификация, а разделение данных на одном устройстве. Любой, кто открыл DevTools, видит и меняет `localStorage`. Для условий ИТиВП Части 1 это допустимо (бэкенда в ней нет), для реального продукта нет.
- Роль `developer` проверяется на клиенте по SHA-256 кода (`site/js/config/roles.js`, `accounts.js`): хеш публичен, код подбирается перебором, роль меняется правкой записи. Это интерфейсное удобство, не граница доступа.
- Хранилище `localStorage` (5 МБ на происхождение, синхронное, без транзакций, без синхронизации между устройствами): достаточно для курса, потолок для продукта.
- У сайта нет общего бэкенда. Он согласован с Частью 2 только по домену (диаграммы, пользователи), но не по коду: сервер ЛР3 и клиент ЛР5 не подключены к `site/`.
- Две реализации «клиента с React»: `site/` (ванильный JS) и `react-app/` (ЛР7–8 Части 1) плюс клиент ЛР5 в `part-2`. Три клиентских стека для одной темы: оправдано заданиями, но дублирует модели данных.

### 1.2 Часть 2 и курсовой

- Цепочка Express, Sequelize, PostgreSQL, JWT (bcrypt), React и axios, MongoDB/Mongoose, Socket.IO, Docker Compose выбрана верно и соответствует тематике ЛР. Слои (маршруты, контроллеры, модели, middleware), проверка ввода на границе, единый формат ошибок, `settings.js` с проверкой секрета JWT (не короче 32 символов, не повтор) при старте: зрелая основа.
- Docker Compose (`lab-08-docker`, `course-project/app/docker`): внутренняя сеть, `read_only`, `cap_drop: ALL`, `no-new-privileges`, лимиты памяти и процессов, healthcheck, порты опубликованы на `127.0.0.1`. Выше требований курса.
- Слабое место организации: работы Части 2 живут в 20+ ветках и 23 рабочих копиях `.claude/worktrees/` с пересекающимися копиями (ЛР1–ЛР5 есть в `25`, `28`, `course-app`). Источник правды один только по договорённости («старшая ветка»), расхождения неизбежны (см. 2.3).
- Курсовой (`course-app`) копирует сервер ЛР3, клиент ЛР5 и compose ЛР8: согласован с лабами, но это копия, а не зависимость, исправления нужно переносить вручную.

### 1.3 Соответствие условиям ИТиВП

Часть 1 и Часть 2 покрывают перечень тем (сеть, окружение, семантика, адаптив, JS, API и хранилища, React, тесты; Node, ORM, auth, React state, React и сервер, MongoDB, WebSocket, Docker, четыре ПЗ, курсовой). Расхождений с условиями не найдено по документам `docs/study/30–32` и `docs/PROJECT-STATE.md`. Риски соответствия: единая тема на всех работах требует, чтобы курсовой не выглядел копией ЛР (в записке показать, что нового: роли, поиск, тесты, compose, документация).

### 2.2 Секреты в репозитории

- В индексе текущей ветки нет ни одного файла `.env` (`git ls-files`), только `.env.example`.
- Во всех локальных ветках (`git ls-tree`) файлов `.env` нет; в истории `.env` не добавлялся (`git log --all --diff-filter=AM -- '*/.env'` пусто). Совпадения по шаблону `.env*` в истории относятся к `.env.example`.
- Реальные `.env` лежат на диске в пяти рабочих копиях (`lab28/part-2/lab-08-docker`, `part2-mongo-work/lab-06-mongodb`, `part2-server-labs/lab-03-auth`, `check-lab12/lab-02-sequelize`, `angry-goldberg/course-project/app/docker`). Они закрыты правилом `.env` из `.gitignore` корня; для `.claude/worktrees/` правило лежит только в `.git/info/exclude` (локально, не едет с клоном).
- Ключи в `.env.example` пустые или заданы подсказкой «сгенерируйте»; значения по умолчанию в compose для паролей отсутствуют (`:?set ... in .env`). Это правильно.

### 2.3 Дубли и расхождения

- `course-project/app/docker/.env.example`: переменная `DEMO_USER_PASSWORD` объявлена дважды (строки 23 и 35). При копировании в `.env` действует последняя, комментарии у двух мест разные.
- `lab-02-sequelize/.env.example` в ветке `23` содержит `SQLITE_STORAGE` и не содержит `POSTGRES_*`/`DATABASE_URL`, а в ветках `25`, `26`, `28`, `lab12` лежит PostgreSQL-вариант. В `course-app/server/.env.example` `SQLITE_STORAGE` закомментирован. Для проверяющего: три версии одной ЛР2.
- `CORS_ORIGIN` и `TRUST_PROXY` читаются в `lab-03-auth/server.js`, а в `.env.example` ЛР3 (ветки `25`, `28`) их нет; в курсовом закомментирован только `TRUST_PROXY`. Значение по умолчанию `http://localhost:5178` зашито в трёх местах (`server.js`, `src/app.js`, `tests`).
- Роль `PORT=3000` стоит в `.env.example` у всех серверных работ (ЛР1, 2, 3, 6, 7, ПЗ1, 2): запустить две одновременно нельзя, а ЛР7 и ЛР6 по заданию часто идут рядом.
- `ADMIN_*` и `JWT_*` повторяются в `lab-03-auth`, `lab-08-docker` и `course-project/app/docker` с одними и теми же именами, но описания комментариев разные.

### 2.5 Валидация и режимы

- Хорошо: `settings.js` останавливает старт при слабом `JWT_SECRET` и недопустимом сроке; compose требует `POSTGRES_PASSWORD` и `JWT_SECRET`; курсовой при `NODE_ENV=production` требует `DATABASE_SSL=true`.
- Плохо: нет единой схемы env. `PORT` берётся как `Number(process.env.PORT) || 3000` (значение `abc` молча даёт 3000), `CORS_ORIGIN`, `TRUST_PROXY`, `MONGODB_URI`, `DATABASE_URL` не проверяются на формат. Различие dev/test/prod есть только через `NODE_ENV` и `config` Sequelize, у ЛР1, 6, 7, ПЗ нет отдельных профилей; `.env.test` нет, тесты полагаются на значения внутри кода.
- Сайт Части 1: `KROKI_URL` имеет значение по умолчанию на внешний `https://kroki.io`; в CSP `connect-src` зашит тот же адрес, поэтому смена `KROKI_URL` без правки CSP не заработает в браузере (браузер ходит через собственный API, серверный вызов не затронут, но запасной путь клиента остаётся жёстко на Kroki).

## 3 Зависимости

- Node: `engines.node >=20` в корне, CI на Node 24 (`.github/workflows/ci.yml`), локально 24.13. Node 20 вышла из поддержки в апреле 2026: нижняя граница в `engines` устарела, стоит поднять до `>=22` (LTS), если нет причин держать 20.
- `npm audit --omit=dev` в корне: уязвимостей нет. В `react-app`: 5 low, цепочка `deepmerge` → `jest-config` → `jest` (инструмент тестов, в продакшен-сборку не попадает).
- Версии в корне и React-приложении современные (`react ^19.3`, `react-router-dom ^7.18`, `vite ^8.3`, `jest ^30.5`), включён Dependabot (`.github/dependabot.yml`).
- Серверы Части 2: `express ^5.1`, `sequelize ^6.37` (v6 в режиме поддержки, v7 всё ещё в альфа/бета-статусе), `bcrypt ^6`, `jsonwebtoken ^9`, `pg ^8`. Критичных замечаний нет; `bcrypt` нативный модуль и усложняет сборку Docker на Alpine (в проекте решено).
- Нет единого файла `.nvmrc`/`.node-version`: версия Node фиксируется только в CI и `engines`.
- По `npm audit` ветвей Части 2 полноценный прогон не делался (23 рабочие копии, у каждой свои `node_modules`); рекомендуется прогнать скриптом перед защитой.
