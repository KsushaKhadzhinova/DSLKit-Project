# Общая стратегия тестирования DSLKit: планы всех видов тестирования

Английская версия: [`01-test-strategy.en.md`](01-test-strategy.en.md). Версия 1.0, 6 ноября 2026, ветка `docs/test-plans-and-checklists`.

Этот документ связывает все виды тестирования проекта в один план и отправляет к подробным планам и чеклистам специалистов в [`specialists/`](specialists/). Он не заменяет существующий комплект [`docs/testing-kulikov/`](../testing-kulikov/) (тест-план 10, чек-листы 11, тест-кейсы 13, матрица трассировки 14, отчёты прогонов 20–95): ссылается на него и добавляет то, чего там нет, то есть охват Части 2 и курсового проекта, порядок прогона и разделение по специалистам.

## 3. Подход

Тестирование смешанное: ручное по тест-кейсам и чеклистам плюс автоматизация там, где она уже есть. Уровни идут от дешёвого к дорогому: линтеры и форматирование, модульные тесты, интеграционные, сквозные, ручные и исследовательские сессии, нефункциональные замеры. Приоритеты: P0 блокирует выпуск или сдачу, P1 важный дефект, P2 заметный, P3 косметика.

Технические правила прогона:

1. `npm test` запускать по одному процессу: порты и временные базы общие.
2. Клиентские тесты Части 2 и `react-app/` запускать на свободной машине (`npx jest -i`, `npx vitest run`), иначе возможны таймауты воркеров.
3. Тесты ЛР2 и ЛР3 запускать без заполненного `.env` (иначе красные тесты настроек).
4. Скрипты e2e запускать в переднем плане, в фоне они зависают.
5. Перед сквозным прогоном выставить ключ `dslkit.tour-done=true`, иначе откроется тур.
6. Команды `docker compose down -v`, `docker system prune` и подобные не запускать без явного «да» владелицы: они удаляют данные.

## 4. Критерии начала и окончания

Начало прогона:

- сборка зафиксирована коммитом, дерево чистое или список отличий записан в протокол;
- `npm install` выполнен, `npm test` в корне зелёный;
- сайт отвечает на своём порту (5173 или 5190, см. таблицу объектов), консоль без ошибок на всех шести страницах `/app/*`;
- для Части 2: база запущена, миграции применены, `.env` заполнен только для серверов, не для юнит-тестов.

Окончание прогона:

- все кейсы P0 и P1 выполнены, открытых дефектов P0 нет;
- открытые P1 имеют решение владелицы (исправить или принять риск);
- чекбоксы чеклистов специалистов заполнены, результаты записаны в протокол прогона с датой, коммитом и окружением;
- матрица трассировки обновлена, новые дефекты заведены с шагами, ожидаемым и фактическим результатом.

Приостановка: блокирующий дефект сборки, недоступное окружение (Docker, Atlas, Kroki), 70% недельного лимита аккаунта. Возобновление: после исправления и повторного дымового прогона.

## 5. Порядок выполнения

| Этап | Что делаем                                                                               | Кто                                 |
| ---- | ---------------------------------------------------------------------------------------- | ----------------------------------- |
| 1    | Закрыть незавершённое из [`00-project-checklist.md`](00-project-checklist.md) (раздел 2) | агент, затем владелица по разделу 3 |
| 2    | Автоматические проверки: `npm test`, `format:check`, `tc:full`, тесты веток Части 2      | автоматизация (02)                  |
| 3    | Дымовой тест и критический путь, затем регрессия                                         | QA (01)                             |
| 4    | API, БД, WebSocket, Docker                                                               | бэкенд (07)                         |
| 5    | Безопасность, доступность, производительность, совместимость (параллельно)               | специалисты 03–06                   |
| 6    | Приёмка документации и отчётов, сверка с условиями                                       | документация (08)                   |
| 7    | Сводный отчёт: дефекты, метрики, остаточные риски, решения владелицы                     | QA (01)                             |

## 6. Метрики

- Доля пройденных кейсов P0–P3 и число открытых дефектов по серьёзности.
- Покрытие модульными тестами (порог 100% строк, ветвей и функций для `npm test` в корне).
- Покрытие требований кейсами по матрице трассировки (`docs/testing-kulikov/14-traceability-matrix.md`).
- Для нефункциональных проверок: Web Vitals, p95 времени ответа, число нарушений WCAG, число расхождений между браузерами.

## 7. Риски

| Риск                                                                 | Что делать                                                                     |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Kroki и внешние сервисы недоступны                                   | проверять поведение при ошибке сервиса, не гонять нагрузку на чужой сервис     |
| Учётные записи в браузере не заменяют серверную проверку (риск R-05) | записать как принятое ограничение, серверную защиту проверять только в Части 2 |
| Нагрузочные тесты нестабильны на загруженной машине                  | вынести в отдельный прогон, фиксировать нагрузку машины                        |
| Нет доступа к Atlas, Postman, Docker Hub                             | пункты помечены «руками владелицы» в общем чеклисте                            |
| Чужие незакоммиченные правки в рабочем дереве                        | прогонять из чистой рабочей копии (`git worktree add`)                         |
| Лимит аккаунта                                                       | останавливаться на 70%, записывать состояние в протокол                        |

## 8. Артефакты

- Протоколы прогонов по шаблону из `specialists/*` (дата, коммит, окружение, результат по чекбоксам).
- Отчёты о дефектах рядом с уже существующими `docs/testing-kulikov/21-bug-reports.md`, `31-api-bug-reports.md`, `42-bug-reports.md`.
- Обновлённая матрица трассировки.
- Сводный отчёт о тестировании (этап 7).
