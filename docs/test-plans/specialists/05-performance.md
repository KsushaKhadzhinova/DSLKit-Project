# Специалист 05. Производительность и нагрузка: тест-план и чеклист

Версия на 6 ноября 2026, ветка `testing-course-full`. English version: [`05-performance.en.md`](05-performance.en.md). Общая стратегия: [`../01-test-strategy.md`](../01-test-strategy.md).

## 1. Роль и область

Инженер по производительности отвечает за скорость, память и устойчивость под нагрузкой. Он не проверяет, правильно ли нарисована диаграмма (это функциональные кейсы), а проверяет, как быстро, какой ценой по памяти и что происходит, когда данных или запросов много.

В области: страницы и редактор (`site/`), собственный движок отрисовки в браузере, внешний Kroki (Graphviz, Mermaid, PlantUML), собственный API `/api/render` (`tools/render-api.js`), service worker `site/sw.js` (кэш `dslkit-v5`, 29 файлов оболочки) и PWA, автосохранение раз в 1000 мс (`source-autosave.js`), localStorage (код, проекты, кэш Kroki на 20 записей с TTL 24 ч, история 5 запусков), 33 примера, серверы Части 2 (ЛР1 REST, ЛР7 WebSocket на socket.io, курсовой с PostgreSQL), Docker-стек ЛР8. Вне области: безопасность и доступность (специалисты 03 и 04), нагрузка на чужой `kroki.io` (по стратегии не гоняем, нужен локальный Kroki).

Важно про движок. Диаграмма это SVG, Canvas используется только для экспорта в PNG (`site/js/utils/exporters.js`). Перетаскивание блока пишет `pos=XxY` в код и перерисовывает всю диаграмму (`canvas-drag.js`). Поэтому «FPS SVG против Canvas» сводится к двум вопросам: сколько кадров даёт перетаскивание и масштаб SVG и сколько стоит экспорт в PNG через Canvas.

## 2. Что проверяет (приоритеты P0-P3)

| Приоритет | Что считается дефектом                                                   | Примеры для DSLKit                                                                                                |
| --------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| P0        | Зависание, падение или потеря данных при допустимом входе                | 150 блоков рисуются 20,1 с, 300 блоков не уложились в 60 с, `/api/render` на 500 вершин 9,5 с и остановка статики |
| P1        | Метрика хуже порога «good» или бюджета, утечка памяти, провал после пика | LCP больше 2,5 с, INP больше 200 мс, рост кучи в долгой сессии, красный spike-тест                                |
| P2        | Заметная, но не блокирующая деградация                                   | медленная холодная загрузка на медленной сети, рост отклика при мягкой нагрузке                                   |
| P3        | Косметика измерений и мелкая оптимизация                                 | лишние запросы, нет `preload`                                                                                     |

Нарушенный порог «good» из Web Vitals это минимум P1. Нарушенное «предложение» без эффекта для пользователя это P2.

## 3. План

### 3.1 Цели

1. Получить реальные числа, которых нет: Lighthouse с категорией performance по страницам, время первой отрисовки для 10/100/1000/5000 узлов, FPS перетаскивания и масштаба, стоимость добавления и удаления рёбер.
2. Найти размер, после которого редактор непригоден, и записать его как предел или предупреждение.
3. Проверить длинную сессию: память, автосохранение, localStorage, service worker.
4. Сделать нагрузочные тесты Части 2 воспроизводимыми и добавить smoke, load, stress, spike, soak там, где их нет.

### 3.5 Окружение, методика, вход и выход

Окружение. Замеры на собранной версии (`npm run build`, `npm run start:prod`), строку «разработка» (`npm start`, отдаёт `site/`) вести отдельно. Машина простаивает (аудит 29.10.2026 дал таймауты из-за параллельных процессов), питание от сети. Записать процессор, ядра, ОЗУ, ОС, версии Node, браузера и Lighthouse, коммит, команду, режим сервера, нагрузку машины (образец `paper-its/bench/env.json`).

Методика. Микрозамеры: 11 прогонов, первый отбросить. Страничные замеры: 5 прогонов, медиана и разброс. API: p95 считать от 100 запросов. Холодный кэш: новый профиль без service worker. Тёплый: после первого визита. Третий вариант: после повышения версии кэша. Менять по одному фактору: размер, число рёбер, сеть, CPU. Рост оценивать отношением времени при удвоении размера (2 линейно, 4 квадратично). Клиент и сервер нагрузки делят процессор машины, это записывать как ограничение.

Вход. Сборка создана, сервер отвечает, среда записана, функциональные P0 проходят, генераторы больших диаграмм готовы. Выход. Все метрики из 3.3 измерены минимум 5 раз и внесены в таблицу раздела 6, открытых P0 нет, у каждого P1 есть решение владелицы, нестабильные тесты Части 2 стабильны на трёх прогонах подряд либо описана причина с данными среды.

### 3.6 Риски

| Риск                                                              | Что делать                                                                      |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Нагрузка на `kroki.io` приведёт к блокировке                      | только локальный Kroki в Docker, на публичный единичные запросы                 |
| Сервер однопоточный, тяжёлый запрос останавливает статику (B-02)  | мерить статику параллельно, пока нет worker threads это P0                      |
| Тесты Части 2 поднимают лимиты и не видят реальных                | отдельные сценарии с лимитами по умолчанию (`maxPerAddress` 20, `maxUsers` 200) |
| «Сырые сокеты» зависят от лимитов дескрипторов ОС                 | записать ограничение ОС, повторить в Docker или на другой машине                |
| Шум фоновых процессов, страницы за входом, состояние localStorage | 5 прогонов, профиль с сессией и `--disable-storage-reset`, чистый профиль       |

## 5. Как запускать

Команды из корня репозитория. Лабораторные лежат в рабочих копиях `.claude/worktrees/`.

```
npm install
npm run build
npm run start:prod
```

`start:prod` отдаёт `dist/` на порту 5173, `npm start` отдаёт `site/` на том же порту (вместе не запускать). Существующие замеры:

```
node --expose-gc paper-its/bench/bench.mjs 11
node testing-course/full/static-sec-perf.js
node tools/serve.js dist 5391
python docs/testing-kulikov/scripts-ui/perf.py
node docs/testing-kulikov/scripts/break-02-api-dos.mjs http://localhost:5173
node docs/testing-kulikov/scripts/part-d-load-static.mjs
```

`perf.py` берёт адрес `BASE` (порт 5391) из `scripts-ui/lib.py`. Lighthouse (в репозитории отчёты версии 13.4.1), мобильный профиль по умолчанию:

```
npx lighthouse@13.4.1 http://localhost:5173/app/editor.html --only-categories=performance --output=json --output=html --output-path=docs/perf/lh/editor-mobile --chrome-flags="--headless=new"
npx lighthouse@13.4.1 http://localhost:5173/app/editor.html --preset=desktop --only-categories=performance --output=json --output-path=docs/perf/lh/editor-desktop --chrome-flags="--headless=new"
seq 5 | xargs -I{} npx lighthouse@13.4.1 http://localhost:5173/ --only-categories=performance --output=json --output-path=docs/perf/lh/landing-{} --chrome-flags="--headless=new"
```

Нагрузка на API (`autocannon` предложен, в репозитории его нет, тело берётся из файла, который создаёт генератор C1):

```
npx autocannon -c 20 -d 300 -m POST -H "Content-Type: application/json" -i docs/perf/payloads/dag100.json http://localhost:5173/api/render
curl -o /dev/null -s -w "%{time_total}\n" http://localhost:5173/
```

Серверы Части 2:

```
cd .claude/worktrees/w-lab21/part-2/lab-01-node-server && node --expose-gc --test tests/stress.test.js
cd .claude/worktrees/part2-ws-work-ee9b7b/part-2/lab-07-websocket && node --expose-gc --test tests/stress.test.js
cd .claude/worktrees/angry-goldberg-bca72d/course-project/app/server && node --expose-gc --test tests/resilience.test.js
```

Docker и база (`DSLKit-Project/part-2/lab-08-docker`, нужен `.env` с `POSTGRES_PASSWORD` и `JWT_SECRET`):

```
docker compose up --build -d
docker stats --no-stream
docker inspect --format "{{.Name}} mem={{.HostConfig.Memory}} pids={{.HostConfig.PidsLimit}} restarts={{.RestartCount}} oom={{.State.OOMKilled}}" $(docker compose ps -q)
docker compose exec db psql -U dslkit -d dslkit -c "EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM \"Comments\" WHERE \"diagramId\" = 1 ORDER BY id LIMIT 100"
```

В браузере: DevTools (Performance, Memory, Network, Application). Автоматизация через Playwright как в `scripts-ui/lib.py` с `performance.now()`, `PerformanceObserver` и `performance.memory` (Chrome с `--enable-precise-memory-info`).
