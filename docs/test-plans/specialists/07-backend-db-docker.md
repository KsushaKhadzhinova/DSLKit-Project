## 2. Что проверяет специалист

| Приоритет | Что считается дефектом такого уровня                                                                                                                                                           |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0        | Падение или зависание сервера, потеря или порча данных, обход входа или ролей, утечка пароля, хеша, секрета или внутренней ошибки, стек не поднимается с нуля, секрет в образе или репозитории |
| P1        | Неверный код там, где контракт задан (500 вместо 4xx, 200 вместо 404 или 409), нет CHECK, внешнего ключа или уникальности, миграция не откатывается, нет записи запроса в БД                   |
| P2        | Расхождение формата ошибки, заголовков, пагинации, сортировки, фильтра, идемпотентности с документацией, тест красный из-за окружения, нестабильные нагрузочные тесты                          |
| P3        | Мелкие отклонения от RFC 9110 (HEAD, OPTIONS, `Accept` с `q=0`), неточные тексты сообщений, устаревшие порты в документах                                                                      |

Проверяются коды 200, 201, 204, 400, 401, 403, 404, 405, 406, 409, 413, 415, 422, 429, 500, 503, единый формат ошибки внутри работы, границы значений, пагинация, сортировка, фильтры, идемпотентность, `PUT` и `PATCH`, миграции вверх и вниз, сиды, `CHECK`, внешние ключи, индексы, транзакции и откат, индексы, агрегации и вложенные документы MongoDB, комнаты, присутствие, `Origin` и переподключение, сборка Docker с нуля, healthcheck, данные после перезапуска, порты 80 и 5000, секреты, `.env`, страницы 500, журнал запросов, снимки каждого эндпоинта.

Факты, которые план обязан учесть:

1. Формат ошибки единый внутри работы и разный между работами: ЛР1, ЛР2, ЛР3, ЛР6 и курсовой дают `{"error":"текст","details":[...]}`, ПЗ2 и корневой API дают `{"error":{"code","message","details"}}`, ЛР7 и ПЗ1 отдают HTML-страницы. Это наблюдение, а не дефект, пока нет решения владелицы.
2. Протокол от 29.10 фиксирует 3 красных теста конфигурации ЛР2 и ЛР3 при заполненном `.env`.
3. Автотесты ЛР2 и ЛР3 идут на SQLite (`SQLITE_STORAGE`), а работа сдаётся на PostgreSQL 16, поэтому ключевые ограничения проверяются и на PostgreSQL.
4. Протокол `30-api-test-run.md` (716 проверок, 661 Pass, 55 Fail, BUG-01 ... BUG-16) старше коммитов `a70e8c0` и `6bcf386` от 30.10, которые ужесточили корневой API. Статус каждого BUG перепроверяется, а не переносится.
5. Коллекция Postman курсового (17 запросов) повторяет ЛР3 без комментариев и тегов, а эндпоинтов 21. Снимки Postman в работах сделаны скриптами, окон Postman нет.
6. Открыты вопросы преподавателю: данные ЛР1 в массиве или в БД (вопрос 31), SQLite или PostgreSQL, нужны ли снимки каждого эндпоинта.

### 3.3 Подход

1. Автотесты каждой работы запускаются по одному процессу (порты и временные базы общие), затем идёт ручной и скриптовый прогон по разделу 4.
2. Техники Куликова, как в `30-api-test-run.md`: граничные значения (0, 1, предел, предел плюс 1), классы эквивалентности (тип поля, Content-Type, метод), предугадывание ошибок (`__proto__`, `\u0000`, `%`, `1e309`, невидимые символы, глубокий JSON).
3. Контракт сверяется с таблицей маршрутов в README и `report.md` работы, а не с памятью. Расхождение кода и документа это P1 (код) или P3 (документ).
4. Ключевые проверки базы повторяются на PostgreSQL 16, потому что автотесты идут на SQLite.
5. Деструктивные команды (`docker compose down -v`, `docker system prune`, `docker volume rm`, `db:migrate:undo:all`, `db:reset`) выполняются только на одноразовой копии стека и после явного «да» владелицы. Этот план их не запускает.
6. Секреты в протоколы не попадают: значения `.env`, строки подключения, токены, вывод `docker compose config` и `docker inspect` не вставляются.

### 3.5 Критерии входа и выхода

Вход: рабочая копия нужной ветки без чужих правок и `npm install` в папке работы. Для ЛР2, ЛР3 и курсового есть PostgreSQL 16 (`docker compose up -d db`), для ЛР6 есть MongoDB, для ЛР8 работает Docker. Автотесты идут без `.env`, ручные прогоны с `.env`. Машина свободна (многие таймауты 29.10 вызваны параллельной нагрузкой).

Выход: пункты P0 и P1 раздела 4 пройдены, открытых P0 нет, открытые P1 имеют решение владелицы. Для каждого эндпоинта есть запись «запрос, код, тело, заголовки» и снимок или объяснение, почему его нет. Протокол хранит дату, ветку, коммит, версии Node.js, PostgreSQL и Docker.

Остановка: недоступны Docker, Atlas или Kroki. Возобновление после восстановления окружения и повторного дымового прогона (`GET /health`).

## 4. Чеклист

### 4.1 Общий контракт API (каждая серверная работа)

- [ ] Таблица маршрутов в README и `report.md` совпадает с реальными маршрутами
- [ ] Успех: `GET` 200, `POST` 201 с `Location`, `PUT` и `PATCH` 200, `DELETE` 204 без тела
- [ ] Неизвестный путь отвечает 404 в формате ошибки работы, неверный метод 405 с `Allow`, `OPTIONS` 204 с `Allow`, `HEAD` как `GET` без тела
- [ ] Тело другого типа (`text/plain`, `application/xml`, `multipart/form-data`) даёт 415 (ЛР1, ЛР2, ЛР3, курсовой, ПЗ2), в ЛР6 проверить, в коде 415 не найден
- [ ] Битый JSON, пустое тело, `null`, массив, число, строка вместо объекта дают 400 с понятным текстом
- [ ] Тело больше `100kb` даёт 413 JSON-ошибкой, затем `/health` отвечает
- [ ] Формат ошибки одинаков для всех кодов работы, `details` содержит пары `field` и `message`

## 5. Как запускать

Автотесты работ, по одной за раз (у каждой рабочей копии свой `node_modules`):

```bash
W=/e/DSLKit-Project/.claude/worktrees
for d in w-lab21/part-2/lab-01-node-server check-lab12/part-2/lab-02-sequelize part2-server-labs-87ed8e/part-2/lab-03-auth lab25/part-2/lab-03-auth part2-mongo-work-6cc76b/part-2/lab-06-mongodb part2-ws-work-ee9b7b/part-2/lab-07-websocket lab28/part-2/lab-08-docker w-pz21/part-2/pz-01-middleware-ejs check-pz22/part-2/pz-02-rest-api angry-goldberg-bca72d/course-project/app/server
do (cd $W/$d && npm test)
done
cd /e/DSLKit-Project && node --test tools/render-api.test.js tools/server.test.js
```

Ручной прогон: `npm start` в папке работы, затем `curl -i http://localhost:3000/health` или файлы `requests.http` в REST Client. PostgreSQL и миграции (ЛР2, ЛР3, курсовой, значения в `.env`): `docker compose up -d db`, `npm run db:migrate`, `npm run db:seed`, откат одной миграции `npm run db:migrate:undo`. Команды `db:seed:undo`, `db:reset` и `npx sequelize-cli db:migrate:undo:all` удаляют данные, их запускать только на одноразовой базе. MongoDB (ЛР6): `npm run seed`, затем `npm run dev`, индексы смотреть в Compass или mongosh.

Docker (ЛР8, отдельный проект, чтобы не задеть рабочие тома):

```bash
cd $W/lab28/part-2/lab-08-docker
docker compose -p dslkit-check build --no-cache
docker compose -p dslkit-check up -d
docker compose -p dslkit-check ps
docker compose -p dslkit-check down
docker compose -p dslkit-check up -d
```

Команда `docker compose -p dslkit-check down -v` удаляет том и данные, её выполнять только на этом одноразовом проекте и после «да» владелицы. `docker system prune` и `docker volume rm` не использовать.

Корневой API и протокол Куликова (результаты пишутся в `docs/testing-kulikov/scripts/results.json`, не коммитить без решения):

```bash
node tools/serve.js site 5195
PORT=5195 node docs/testing-kulikov/scripts/run-all.mjs
node docs/testing-kulikov/scripts/make-report.mjs
```
