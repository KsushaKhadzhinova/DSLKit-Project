# Требования преподавателя к отчётам и коду (Часть 2, вариант 26, чётный)

Источник: замечания по ПЗ1 и требования из чата группы (2026-10-09 и 2026-10-02), пересказ владельца. Проверять перед защитой. Вариант 26 чётный: логирование и первая работа идут через **таблицу БД**, не через файл.

## Код (ПЗ1 и по аналогии во всех работах)

1. Чётный вариант: middleware логирования пишет запросы **в таблицу БД** (нечётные пишут в файл). Если запись не удалась (БД недоступна, сбой), не молчать: показать **страницу 500**.
2. Последовательность обработчиков такая, чтобы при ошибке открывалась оформленная страница 500, а не текст на чёрном фоне.
3. Проверка вводимых значений: непустое поле (в том числе пробельное), ограничения длины, числовые поля `>= 0`.
4. Чтобы записи визуально не совпадали, показывать у каждой записи уникальное поле «время создания».
5. Ограничения (длины строк, пределы чисел) вынесены в **отдельный файл** (`limits.json` или `.txt`), а не размазаны по коду.
6. На сайте есть ссылка на страницу 500 для демонстрации.

## Отчёт

1. Цель работы нумеруется («1 Цель работы»); раздел называется «Заключение», не «Выводы».
2. Страница с текстом заполнена минимум на 25 % (около 11–12 строк), не пустые листы.
3. Рисунок и его номер на одной строке (неразрывный пробел: Ctrl+Shift+Пробел), подпись «Рисунок N – Описание» с большой буквы, описание содержательное (что именно изображено), подпись не уже рисунка.
4. Рисунки размещаются **по тексту**, не в приложении: сверху описание, снизу рисунок. Каждую ошибку и функцию описывать с рисунком, иначе унифицировать или убрать лишнее.
5. Не писать «(см. рис. 1)». Ссылаться словами: «элемент показан в верхней части рисунка 1», без скобок и слов «смотреть».
6. Кавычки только «ёлочки», не "".
7. Гиперссылки без синего выделения (обычный цвет текста).
8. Приложения небольшие, лучше несколько; название точно отражает содержимое; длинное название переносится в содержании; в содержании у приложения указан раздел, где на него ссылаются.
9. Слова-паразиты убрать («также», «были» и т. п.); порядковые и количественные числительные записывать по правилам СТП.
10. Окончания «Проверил(а)» и подобные в оформлении не забывать.
11. Описать блоки: страница 500 (развёрнуто) и форма (какие проверки на введённые значения).
12. **Контрольные вопросы: отвечать только на n−1, n, n+1 своего варианта.** Вариант 26 по кругу: для списка из 30 вопросов это 25, 26, 27; из 16 вопросов 9, 10, 11; из 10 вопросов 5, 6, 7. В `tools/build-report.js` для этого есть блок `{{answers}}…{{/answers}}`. Это отменяет прежнее решение «ответов не нужно» для Части 2 (для Части 1 решение остаётся).

## Что ещё проверить перед защитой (найдено по аналогии)

- Номера разделов и рисунков идут подряд, ссылки на них в тексте не битые.
- Нет пустых страниц, заголовки не оторваны от текста.
- Ссылки на ветки репозитория точно такие, как в условии: lab21, lab12, 23, 24, 25, 26, 27, 28, pz21, pz22, pz23, pz24.
- В README каждой работы: что сделано, как запустить, имя ветки.
- Проверка пробельных значений и лимитов символов во всех формах и API, одинаковая в клиенте и сервере.
- Страница 404 и 500 оформлены в стиле сайта, не стандартная заглушка сервера.
- Нет секретов и `.env` в репозитории, есть `.env.example`.
- Скриншоты: подписаны, видны URL и результат; отложены по решению владельца, но к защите нужны.
- Тесты зелёные, сервер запускается с нуля по README на чистой машине.
- Спросить у преподавателя то, что не подтверждено: правило «круга» для вариантов, SQLite вместо PostgreSQL, React Router 7 вместо v6.
