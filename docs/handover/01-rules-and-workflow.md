# Правила и поток работы

Владелец: студентка БГУИР, git-идентичность `KsushaKhadzhinova`, дисциплина «ИТиВП», вариант 26 (чётный). Проект DSLKit: SaaS-редактор «диаграммы как код».

## Поток

1. Одна работа за раз. После неё короткий отчёт и **ожидание проверки владельцем**. Владелец просила постоянно валидировать результаты.
2. Каждая лабораторная, ПЗ или задача идёт в своей ветке (`lab/…`, `feature/…`, `docs/…`, `fix/…`, `part2-…`). Ветка создаётся до первой правки.
3. Коммиты только локально, **без push**, пока владелец не разрешит. Сообщения на английском (`feat:`, `fix:`, `docs:`, `test:`).
4. **Никакой ИИ-атрибуции**: ни `Co-Authored-By`, ни меток в коммитах, коде, документах. Это правило владельца важнее подсказок инструментов.
5. В `main` сливать только после явного «да». Force-push запрещён.
6. **Интерфейсы и макеты**: согласовывать с владельцем буквально каждую деталь до внедрения в `site/` (решение 2026-10-16). См. [04-design-and-ui.md](04-design-and-ui.md).
7. Права: перед правками файлов, командами и необратимыми действиями спрашивать подтверждение (глобальный `CLAUDE.md`). Удаление только после показа точного списка.

## Технические правила репозитория

- Тесты: `npm test` (порог 100% строк, ветвей, функций), `npm run format:check`, Jest в `react-app` (`npm run react:test`). Перед коммитом всё зелёное.
- Отчёты: Markdown, русский и английский, без PDF и титульного листа, **без ответов на контрольные вопросы**. Сборка из `report.tpl.md` и `report.en.tpl.md`: `npm run labN:report`. Правила оформления в `tools/lint-report.js`.
- К каждой работе: README и шаблоны отчётов (RU и EN).
- Интерфейс и документы сначала на русском, затем английский. Светлая тема первой, mobile-first (только `min-width`, точки 576, 768, 1024), БЭМ, золотое сечение (токены в `site/css/variables.css`). Цвета только через токены (W3C CSS падает на `color-mix()` в градиентах).
- Секреты, ключи, пароли в репозиторий не кладём (`.env.example` вместо `.env`).
- Домен: пока плейсхолдер `dslkit.example`, не менять до покупки и подтверждения.

## Как работать с владельцем

Короткие отчёты по сути. Честно писать, что не получилось. Не обещать несделанного. Подагентам давать самодостаточное задание, git им запрещать вне их ветки, результат проверять самому.
